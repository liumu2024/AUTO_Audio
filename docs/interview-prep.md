# 面试准备：可编辑时间线的 AI 视频导演 Agent

> 用法：正文（§0–§20）是面试答案，全部用人话写，不出现内部函数名/事件名；附录是内部名词对照表，只给自己对照代码用，面试别念。正文指标与最新简历口径一致，数字背后都有评测报告支撑。

## 0. 一句话定位

我不是在做“文生视频”工具，而是在做**让大模型当导演的 Agent 系统**：模型不直接出片，而是产出**一份可审查、可修改、可版本化的视频方案**，再编排外部能力（生成模型、视频处理、渲染器）把它做成成片。生成模型只是可替换的执行器之一。它还维护**创作记忆**：用户的长期偏好与当前项目要求都会被沉淀、复用和失效管理，让 Agent 越用越懂用户。

## 1. 三分钟讲法

1. **背景**：早期版本是“样例视频风格迁移”，前端直接调接口出片，方案生成完就没法改、状态也到处漂移。所以我做了一次重构：把“出片”拆成“导演编排”。
2. **核心机制**：一份视频方案被拆成三层——**草稿**（正在编辑）、**修订**（每次改动留下的不可变快照）、**渲染**（针对某个版本执行一次出片）。改只允许改用户点名的片段，其他一律原样保留；第二次渲染不会覆盖第一次的产物。所有执行、校验、存档都收在服务端一处，前端只负责展示。
3. **工程方法**：审查分三类（硬约束严格、输入宽容、语义交给模型判断）；评测分三层（离线自检、真实模型回归、真实出片），真实模型核心套件 3 次重复运行、51/51 轮确定性检查全部通过；每次失败登记“根因是谁、怎么修、怎么验证”，新规则必须带反例测试。
4. **一句话总结**：把“大模型出片”变成“大模型编排一份可追溯、可二次修改的视频方案”，这是它和普通 AIGC 的本质区别。

## 2. 项目背景类

**Q：解决什么问题？**
早期是“样例迁移+直接出片”，用户拿到的是不可编辑的成品，改一个词就要重来；前端和后端各有一套执行逻辑，状态对不上。重构后变成“导演对话 → 结构化方案 → 局部修改 → 版本化渲染”，每一步都可回放、可追溯。

**Q：规模？**
一个仓库六个部分：前端、后端、前后端共享的协议、渲染工程、桌面壳、评测数据集。核心逻辑在“导演服务”和“执行管线”两块。

**Q：技术栈？**
TypeScript 全栈（前后端共享同一套类型定义，协议错误在编译期就能暴露），前端 React，后端 Express，本地用文件模拟数据库、正式环境用关系库，渲染用现成的渲染引擎，视频处理用 FFmpeg，画面生成接云端大模型（接口可替换）。

**Q：这个项目做得好不好，有数据吗？**
真实模型回归的核心套件 3 次重复运行，51/51 轮确定性检查全部通过：工具/技能选择准确率 100%、未授权执行 0 次、知识写入精确率/召回率 100%、草稿创建/修订与失败恢复完成率 100%；回复质量由独立裁判模型评判，通过率 92.2%（51 轮）。口径要说清楚：确定性检查是程序断言（动作、工具、状态、版本是否正确），回复质量是另一个模型的独立评价，不是自己给自己打分。

## 3. 架构类

**Q：整体分层？**
三层：
- **输入展示层**（前端）：收用户的自然语言和素材，把后端推过来的进展渲染出来；不自己执行任何业务动作。
- **决策调度层**（后端上半）：理解意图、维护“当前项目要求”和“长期偏好”、决定这一轮要调用哪个能力。
- **执行管线层**（后端下半）：规划方案、按范围修改、解析素材、标准化、渲染出片、留证据。
三层之间靠一份**统一的时间线协议**衔接：前端展示、后端校验、渲染器读取的都是同一份结构。

**Q：一条请求怎么走？**
用户说话 → 前端发起一条长连接请求 → 后端恢复本次会话 → 把相关记忆带进来 → 模型理解并决定要做什么 → 先落“要求/记忆”这类状态 → 校验工具和权限 → 执行（生成方案/修改/渲染）→ 结果经同一条连接推回前端 → 最后把权威会话状态同步给前端。

**Q：为什么执行权必须在服务端？**
因为“谁执行、改了什么、存成哪个版本”必须是**唯一事实**。前端如果也能执行，就会出现同一操作两端跑、状态对不上的问题。前端只消费事件，服务端是唯一权威，出了任何问题都只查一个地方。

**Q：三个核心实体？**
- 草稿：你正在编辑的当前版本。
- 修订：每次改动保存下来的**不可变快照**，旧版永远在，随时能回看“第几版改了什么”。
- 渲染：针对某个具体修订执行一次出片，记录“基于哪个版本、用了哪份方案”。

**Q：二次渲染会不会把第一次的结果删掉？**
不会。每次渲染是独立记录、独立产物目录；第二次渲染基于新修订创建新产物，第一次的 MP4 原样保留。我们有自动化测试断言“两条渲染记录并存”，也真实跑出过同一会话三个版本的成片同时存在。

## 4. 核心设计决策

### 4.1 审查三分法
- **硬约束**：版本不能丢、授权外不能改、没改不能假装改、交付必须用户授权——这类严格、程序说了算，绝不为模型方便放宽。
- **输入校验**：模型传的参数合不合法——这类**宽容**，允许模型用自然方式表达，只拦会破坏状态或越权的输入。
- **语义判断**：改得对不对、回答切不切题——这类**不写死规则**，交给另一个模型当裁判，或用语义匹配兜底。

踩过的坑：我曾把“只有部分范围能带目标镜头”写成输入硬规则，结果模型在“只改某一镜字幕”时自然带上目标镜头，被误拒，一次评测挂 6 轮。从此确立：**输入要宽容、状态要严格**，新规则必须带“正常用法会不会被误伤”的反例。

### 4.2 按范围修改
用户说“只改第二镜的转场”，系统只允许那一块变化：候选方案里其他镜头的画面、字幕、转场、音频一律按旧版保留；如果模型最终其实什么都没改，系统也会拒绝保存（防“假装改过了”）。四种常见范围：只改字幕、只改某个镜头、只改某个镜头的视觉呈现、整体重排。

### 4.3 目标场景由服务端确认
模型给的“镜头编号”不可信（实际出现过模型编造编号的情况）。所以系统会拿它和当前方案的真实镜头对照：对得上才用，对不上就友好拒绝并列出可用镜头；用户没指定时，回退到当前选中的镜头。**身份由系统绑定，不信任模型字符串。**

### 4.4 记忆分两级（创作知识沉淀）
- **长期偏好**（跨项目）：“我做的片子都偏蓝灰低饱和”——记一次，以后所有项目都参考；用户能查看、撤销、删除。
- **当前项目要求**（单项目）：“这一版旁白要冷静克制”——只对这一部生效，是“这单的合同”。

保护机制：每条记忆都有**作用域**（用户级/草稿级）和**状态**（生效/候选/已撤销）；模型“猜”出来的偏好只能作为**候选**，经用户确认才生效；撤销过的偏好不会被悄悄复活；同一件事在多个项目里反复出现但没有被否定，也降级为候选而不是直接变成规则。

使用方式：每轮规划前按作用域**召回**相关记忆并注入规划上下文，候选记忆只展示、不参与创作；写入、召回、失效都有来源追溯，可审计。真实模型评测中，知识写入精确率/召回率与作用域准确率均达 100%。

### 4.5 渲染绑定版本
每次渲染记录“基于第几版、用了哪份方案快照”。第二次渲染用新修订，第一次的产物与记录原样保留。这是“可编辑时间线”能成立的关键：方案可改、版本可溯、渲染可重复而不互相破坏。

### 4.6 留证据（可观测性）
每轮对话、每次规划、每次渲染都写证据：会话有事件流，操作有独立目录，关键结果（输入、模型调用、工具结果、范围过滤、最终版本）都有文件。原则是**证据可回放、内容可精简**——审计只留必要项和统计，不把几百行明细全塞进去。

### 4.7 评测体系
- 第一层**离线自检**：不花钱、不动模型，验证协议、边界、版本正确性，几十个脚本每次改动都跑。
- 第二层**真实模型评测**：让真模型按核心套件（13 个多轮场景、25 个轮次）对话，看它会不会选对工具、改对范围、记对要求、正确地拒绝不该做的；3 次重复运行 51/51 轮确定性检查全部通过，回复质量通过率 92.2%（51 轮），知识写入精确率/召回率 100%。
- 第三层**真实出片**：真正调生成模型、视频处理、渲染器，产出可播放的 MP4。

配套一套**失败登记制度**：每次失败登记根因、修复方式、验证方式；新规则必须带反例测试；后端拒绝操作时写明是哪个环节拒的（参数、目标、范围、版本门禁、结构校验等）。这解决了“规则反复改还遗漏”的问题——不再靠手感，而是有据可查的闭环。

## 5. 高频技术问题（人话）

**Q：长连接推送（SSE）怎么做？**
前端发一个普通 HTTP 请求，后端不立刻返回，而是把这一轮进展像直播一样一小条一小条推回来，连接保持到本轮结束。事件按**角色**分四类：
1. 过程提示：展示“正在理解、正在检查”这类状态；
2. 执行进度：选中了哪个能力、开始做什么、进度多少、成功还是失败；
3. 最终结果：给用户看的回复；
4. 状态同步：每轮结束把服务端权威的会话状态推给前端刷新界面。

**Q：为什么不用 WebSocket？**
因为这是一问一答的单向推送：一个 HTTP 连接足够，还能复用现成的鉴权和错误处理；双向长连接在这里是多余能力。

**Q：重复提交怎么防？**
每次提交带一个稳定的请求号；服务端用“会话+请求+序号”生成内部唯一标识，重复的标识直接拒绝。

**Q：两个人同时改一个方案怎么办？**
保存修改时要求“你基于的版本必须还是当前版本”，对不上就报冲突，不会静默覆盖别人的修改。

**Q：本地和真实环境怎么切换？**
本地用文件模拟数据库（评测和桌面开发都在用），正式环境用真实数据库；上层代码同一套接口，切换只改配置。

**Q：中文文本匹配怎么做？**
先把文本归一化（去空格、统一写法），再切短词（中文切两字组合），必要时用“语义兜底”：两段话只要一半左右的词重合，就认为相关。这解决“模型换了个说法但意思一样”被误判的问题。

**Q：安全上怎么防恶意输入？**
三件事：用户身份、草稿、版本这类系统字段由服务端绑定，模型传了直接拒；交付动作必须用户明确授权；外部地址有校验，拒绝让生成模型访问内网/本机地址（防被利用去探测内网）。

**Q：生成模型断了怎么办？**
生成能力做成可替换接口：配置指向真实服务就真实调用；不配置就明确失败并走兜底画面，**绝不假装成功**。评测环境会刻意关掉生成来省成本——这同时也是我踩过的坑：**评测环境≠真实运行环境**，查问题必须先分清。

**Q：图片怎么给生成模型？**
生成模型要求“公网可达的图片地址”。所以：用户本地上传的图片，系统在规划前会自动发布成可达地址再用；已经公网的图片原样透传。本地测试时把发布地址指向局域网可达地址即可，真实公网用对象存储发布。

### Agent 专项追问（记忆 / 压缩 / 结构化输出 / 工具编排）

**Q：上下文压缩怎么做，会不会丢关键事实？**
保留最近四轮原文，更早内容滚动压缩成摘要；已确认的创作约束和记忆不在压缩范围，每轮执行结果以事实形式回写会话。有专门测试断言“压缩后约束仍在”，评测里对话事实召回率 100%。

**Q：创作记忆怎么防脏数据？**
三件事：模型推断的偏好只能作候选、必须用户确认才生效；撤销过的记忆不会复活；每条记忆记录来源（哪一轮、哪句话），可追溯。评测中“无关知识写入、跨作用域泄漏、虚假保存声明”均为 0。

**Q：记忆怎么参与创作？**
规划前按作用域召回：用户级偏好进所有项目，草稿级要求只进当前项目；候选记忆只展示不参与创作；召回结果标注命中词，可审计。

**Q：结构化输出为什么一次通过率高？**
模型看到的工具参数和输出都是 JSON Schema；服务端先校验再执行，字段错或范围不对直接拒绝；首次失败只发一次格式修复请求，二次失败走确定性降级，不会让整轮对话崩掉。评测中结构化一次通过率 100%、降级率 0%。

**Q：工具和技能为什么分开注册？**
技能说明“这类任务怎么做”（含具体操作指令），工具是“具体动作”。模型必须先选中技能、再绑定该技能名下的工具，同轮校验；这防止模型绕过业务边界凭空调用动作。选错了服务端会拒绝并给出可用替代项。

**Q：交付授权怎么判断，不怕模型假装用户授权吗？**
授权不靠匹配“渲染”两个字，而是看模型本轮**连贯决策**：意图必须是执行、且明确要求交付，两者同时成立才放行；前端界面操作只算展示，不构成授权。评测里“未授权执行 0 次”测的就是这条。

**Q：模型选错工具或改错范围怎么办？**
执行前先做就绪检查（缺素材、没草稿、没授权都直接拒绝并给替代方案），再校验参数与范围；拒绝时返回结构化原因和恢复建议，失败结果回写会话，下一轮模型可以修正重试。真实评测里失败恢复完成率 100%。

**Q：这些 100% 会不会是过拟合测试集？**
不会只看一套数：确定性检查是程序断言（动作、工具、状态、版本对不对），回复质量由独立模型裁判；评测分离线、真实模型、真实出片三层，记忆评测另用 holdout 场景，防止只对测试集有效。

**Q：时延和成本怎么控制？**
每轮记录模型调用次数和 token；纯讨论轮不触发任何工具；失败后恢复走非执行回复；评测默认关闭真实生成来省成本。核心套件单轮决策 p50≈9.1 秒、p95≈61.4 秒。

## 6. 踩坑故事（挑一两个讲）

1. **规则误伤正常表达**：为了支持“改视觉呈现”，我加了一条“目标镜头只允许在部分范围使用”的规则，结果模型在做“只改某一镜字幕”时自然带上目标镜头，被误拒 6 轮。教训：输入宽容、状态严格；加规则先想反例。
2. **评测环境 vs 真实环境**：我曾断言“生成模型从没被真实调用过”，后来发现是评测脚本强制关了生成，而真实运行配置是开着的——云平台有真实调用消耗、也产出了 20MB 真实成片。教训：环境问题先分清评测覆盖和真实运行。
3. **语义被写成字符串匹配**：一度以为“跨轮要求保留率低”是上下文管理问题，实际是模型换了说法、而断言要求精确词。改成语义判断后，问题才真正归因清楚。

## 7. 边界与诚实清单

- 没做：语义向量检索（关键词方案够用，且用更难的数据集量化过差距）；独立音轨（已取消）；渲染组件沙箱。
- 生成质量不是本项目的卖点；卖点是**编排正确性、可验证性、评测驱动**。
- 真实公网素材发布：代码路径已通，端到端验证需要外部对象存储凭证。

## 9. 可以反问面试官的问题

1. 你们对 Agent 输出正确性的验收方式是什么——数据集、门禁，还是人工抽检？

## 10. 工具调用类（Agent 岗高频，几乎必问）

**Q：Agent 为什么要调用工具？**
因为大模型本身有三大短板：信息是训练时的（要查实时数据）、只能输出文字（没法真正操作业务）、回答靠概率（需要确定性校验）。工具就是补这三块：实时性、操作性、确定性。

**Q：Function Calling 和你的方案是什么关系？**
我们不用模型厂商的原生 Function Calling，而是让模型输出一份**结构化的工具请求 JSON**，由后端解析、校验、执行。这样协议与厂商解耦——换模型不改业务协议。原生 Function Calling 未来可以作为“适配层”，但内部仍然翻译成同一份协议。

**Q：模型和后端各自负责什么？**
模型负责“理解和表达意图”：选哪个工具、传什么参数、依赖什么；后端负责“执行与把关”：参数校验、身份/版本绑定、权限、幂等、真实执行、结果回写、失败处理。一句话：**模型提议，后端决定。**

**Q：工具调用上线后有哪些工程风险？你们怎么防？**
- 参数幻觉 → 严格 schema 校验，系统字段后端绑定，模型传了直接拒；
- 越权/误操作 → 交付必须用户授权，动作分只读/改草稿/交付三档；
- 重复调用 → 稳定请求号 + 服务端去重；
- 工具失败 → 结构化失败 + 恢复建议，绝不假装成功，也不把失败状态写进正式版本；
- 成本放大 → 工具卡精简、一次能做完不让模型绕路、失败不盲目重试。

**Q：工具很多时模型怎么选？**
给模型的是“精简能力卡片”而不是全部细节：每个工具只有名称、作用、成本档、输入要求；选中后才加载完整说明。避免把所有能力细节塞进上下文稀释注意力。

**Q：工具返回失败后怎么处理？**
统一转成结构化失败：发生了什么、为什么、怎么恢复；同时把失败原因写进证据链（并标注是哪个环节拒的），下一轮可以继续而不是卡死。

## 11. 评测类（“Agent 怎么评测”是高频大题，参考业界八维框架）

**Q：Agent 评测和普通模型评测有什么区别？**
普通问答看“答案对不对”；Agent 是多步执行系统，要同时看结果、过程、工具、成本、稳定性、安全。只看最后一句答没答对，会漏掉“过程很糟但结果碰巧对”的大量问题。

**Q：你从哪些维度评？**（用八维框架 + 我们的做法）

| 维度 | 我们怎么做 | 数据/证据 |
|---|---|---|
| 任务完成率 | 真实模型 58 轮剧本，逐轮断言“该建的方案建没建、该改的改没改” | 旧基线确定性通过 27/58，意图准确率约 86% |
| 结果质量 | 独立裁判模型评自然回复，另有人工抽检计划 | 回复质量通过率约 91% |
| 过程质量 | 断言“该用工具时用了、不该用没用、没改不能假装改” | 有专项断言（工具选择、范围、零差异） |
| 工具调用质量 | 校验工具选得对不对、参数合不合法、结果成不成功 | 工具选择准确率约 86% |
| 检索质量 | 偏好记忆召回按 easy/hard 两套集测 | easy Recall@8=100%，hard=75% |
| 性能与成本 | 记录单轮耗时与 token | p50≈5.3s、p95≈43s；58 轮约 60 万 token |
| 稳定性 | 失败恢复轮、工具失败降级轮 | 有专项轮次，不注入失败时不误判 |
| 安全与权限 | 未授权执行、越权改草稿、系统字段覆盖均为 0 | live 里这几项全部为 0 |

**Q：离线评测和在线评测？**
离线：冒烟集（核心链路能不能跑通）、回归集（历史问题不复发）、行为评测集（该不该调用工具、失败后怎么降级）、安全评测集（越权/敏感操作）。我们就是这套的离线版。在线：真实上线后看任务完成率、错误率、延迟、成本、用户反馈——**我们目前没有真实线上流量，这是诚实要讲的**；但 trace/事件流/失败台账就是为“上线后可定位”设计的同一套思路。

**Q：LLM 当裁判可靠吗？**
不可全信。原则是：**规则能判的用规则，结果能验证的用结果，只有主观评价才用裁判模型 + 人工抽检**。我们就是这样：意图/工具/范围/版本用确定性断言，回复质量才交给裁判，且关键轮次有人工抽检计划。

**Q：失败样本怎么回流？**
每次失败登记“根因、修复、验证”，沉淀进回归集；新规则必须带“会不会误伤正常表达”的反例。这就是持续迭代闭环——项目里叫“失败登记制度”。

## 12. 记忆与上下文工程类

**Q：LLM 无状态，怎么让它记住多轮对话？**
分层：最近几轮原文 + 更早内容的滚动摘要 + 结构化“当前项目要求”台账 + 跨项目长期偏好。前端刷新不丢：工作区会话由服务端持久化，恢复时带回草稿、版本、要求。

**Q：短期记忆和长期记忆怎么区分？**
短期=本会话的工作区状态（草稿、版本、最近结果）；中期=本项目的“要求台账”（这单的合同）；长期=跨项目的创作偏好（以后都这样）。三者写入时机、有效期、用户可见性都不同。

**Q：记忆会不会过期或冲突？**
会，所以有机制：要求可以被显式替换/撤销；偏好有“待确认候选”状态，模型猜的不能直接生效；被撤销过的偏好不会被悄悄复活；当前输入永远压过历史记忆。

**Q：为什么没用 RAG？**
诚实讲：本项目需要“召回”的是用户偏好而不是文档知识，语料很小，关键词方案够用；而且我们用更难的数据集量化过差距（hard 集 Recall 降到 75%），向量检索作为明确的后续项，而不是没考虑过。

**Q：什么是上下文工程？你们做了什么？**
让模型在有限上下文里看到“该看的、最新的事实”：服务端只把权威状态（草稿版本、有效要求、召回偏好、工具能力卡）注入，不加旧文案和冗余历史；最近几轮原文保留、更早的压缩成摘要。

## 13. 系统设计与扩展类（可能被要求“现场设计”）

**Q：怎么新增一个能力（比如加一种修订范围）？**
讲出我们的扩展点流程：定协议（输入 schema）→ 定义“允许改什么”的范围表 → 接入统一的门禁（没改不能假装改）→ 加目标绑定与校验 → 加反向用例测试 → 登记规则台账。面试官会认可“有一套固定扩展流程”而不是临时改。

**Q：怎么保证正确性和一致性？**
四个词：**唯一权威**（执行都在服务端）、**不可变**（修订只增不改）、**版本保护**（改的时候必须基于最新版，冲突就报错）、**门禁**（没改不能假装改、越权字段一律丢弃）。

**Q：怎么控成本与延迟？**
工具卡精简省 token、确定性方案兜底省一次模型调用、评测环境关生成、素材生成并发可配置。实测单轮 p50≈5.3s 主要是模型本身耗时。

**Q：怎么扩展多用户/生产化？**
会话、草稿、记忆都按用户隔离；本地用文件库、生产用关系库同一套接口。诚实讲：当前形态偏单机/本地，生产化要做部署、监控、配额，这些是明确的后续项。

**Q：ReAct 和你的方案什么关系？**
我们的模式可以看作 ReAct 的工程化变体：模型“想（规划）→ 提议工具”，但“执行与验证”在服务端完成，并且每一步都有审查门禁和证据记录；比起纯 ReAct 的“模型反复自循环”，我们把确定性控制从模型手里拿回到系统手里。

**Q：生产落地最大的难点是什么？**
模型行为的不稳定与系统规则之间的平衡：规则太严误伤正常表达，太松又不可控；所以核心是“输入宽容、状态严格、语义交给模型”，并靠失败登记制度持续校准。

## 15. Agent 基础与框架选型（八股速答）

**Q：什么是 AI Agent？核心组件是什么？**
Agent 是“能自己决定下一步做什么”的程序：理解目标 → 拆解步骤 → 调用工具 → 看结果 → 调整。核心组件是规划（拆任务）、记忆（记住上下文和偏好）、工具（操作外部世界）、行动（执行并反馈）。普通问答模型只做最后一环，Agent 把四件事串成一个循环。

**Q：ReAct / Plan-and-Execute / Reflexion 各是什么？你们属于哪种？**
- ReAct：每步“想一下 → 做一下 → 看一眼结果”再继续，适合边做边调整的任务；
- Plan-and-Execute：先一次性定计划再逐步执行，适合计划相对稳定的任务；
- Reflexion：做错了先自我复盘，把教训写进记忆再重试。

我们更接近 Plan-and-Execute 的工程化变体：每轮先理解意图、确定要动的范围，再执行；执行中每一步都有校验和记录，不会让模型无限自我循环。这正好契合“视频方案修改”的场景——用户要的是可控的局部修改，不是自由探索。

**Q：为什么不用 LangChain/LangGraph，为什么自研？**
因为核心难点不是“调工具”，而是“可编辑时间线的状态机”：草稿/修订/渲染三层版本、按范围修改、没改不能假装改、创作记忆作用域。这些是业务状态约束，框架给不了；自研让我们能控制每一处校验和证据记录。诚实讲：如果现在重做，我会认真评估 LangGraph 的状态图能否直接表达“修订版本链”，但当时的自研决策是合理的，且换模型、换生成服务时协议不用改。

**Q：单 Agent 还是多 Agent？为什么？**
当前是单 Agent（导演模型）+ 技能/工具编排，而不是多个子 Agent。原因：决策链集中在“一份视频方案”上，单 Agent 持有完整上下文最不容易把要求传丢；多 Agent 引入的状态同步、结果传递、责任边界问题，在这个规模下是纯成本。如果以后要加“审查 Agent 独立复核导演方案”，正确姿势是：审查 Agent 只读输出评审意见，导演 Agent 决定是否采纳——评审不直接改方案，避免双写冲突。这也是“一个写代码一个审查怎么协作”这类问题的通用答案。

**Q：MCP 是什么？和你的技能/工具体系什么关系？**
MCP 是让 Agent 连接外部工具/数据源的标准化协议：服务端统一暴露资源、工具、提示词。我们的技能/工具注册表本质上是同一思路的轻量实现：工具 = 具体动作（登记参数 schema），技能 = 一类任务怎么做（含操作指令），模型必须先选技能再绑工具。接外部服务时用 MCP 标准暴露更省事；但内部核心工具仍走自己的协议，因为要带版本、范围、门禁这些业务语义。

**Q：原生 Function Calling 的原理是什么？为什么你们不用？**
原生 Function Calling 是模型厂商内置能力：你在请求里声明一批函数（名称 + JSON Schema），模型输出“调用哪个、传什么参数”的结构化结果，由你的代码执行。本质是把工具清单写进上下文 + 让模型按格式输出。我们不直接用，是因为协议要与厂商解耦（换模型不改业务代码），且我们的工具参数要带“目标镜头、修订范围、基于哪个版本”这类业务字段，需要服务端强校验。原生 Function Calling 可以作适配层保留，内部翻译成同一份协议。

**Q：LLM 基础速答：幻觉、temperature、JSON 输出、上下文窗口、模型选型？**
- 幻觉：模型生成训练数据里没有或与事实不符的内容，本质是概率生成没有“事实核查”。缓解：工具返回的事实直接注入、结构化校验、精确数字从工具结果提取而不是让模型背。
- temperature：控制随机性，越低越确定。工具调用相关输出用低温度，创意文案用中高。
- JSON 输出：用 schema 约束格式，但服务端永远再校验一次，不信任模型输出。
- 上下文窗口：模型能同时看到的最大 token 数，超了会截断或报错，所以要精选注入 + 压缩。
- 模型选型：按任务分档——意图路由和工具调用用便宜稳定的模型，创意和复杂推理用更强模型。一句话：简单任务不请贵模型。

## 16. Loop Engineering 与 Badcase 闭环

**Q：什么是 Loop Engineering？你们怎么做的？**
把 Agent 的“循环”从 while(true) 变成可控工程：循环条件、步数限制、状态更新、异常处理、观察裁剪。我们单轮循环内：模型决策 → 后端校验 → 执行 → 结果回写；每轮有明确结束标志（用户收到回复、状态同步）；失败不盲目重试（一次格式修复请求，再失败走确定性降级）；工具返回内容精简成事实回写，不把几百行明细塞回上下文。

**Q：Checkpoint / 状态回退 / trace 回放怎么做的？**
- Checkpoint：草稿的每个修订版本都是不可变快照（改前快照 + 改后快照），任何时候能回答“第几版改了啥”；
- 状态回退：失败时草稿不落新版本，工作区保持上一稳定版，下一轮模型可以修正重试；
- Trace 回放：每轮对话、每次工具调用、每个拒绝点（带环节标记）都写证据，出问题按时间线回放“模型怎么走到这一步的”。

**Q：出现 Badcase 怎么快速定位环节？**
三步：先看 trace 时间线（哪一轮、选了哪个工具、参数是什么）；再看拒绝点标记（参数校验拒的、范围校验拒的、版本冲突拒的、没授权拒的——每处都写清环节）；最后归因：是模型理解错、规则误伤、还是上下文没带够。归因后进失败台账，标“根因、修复方式、验证方式”。

**Q：Prompt 调优“修好一类、坏了另一类”怎么解决？**
这是规则/提示词的回归问题。我们的机制：新规则必须带反例测试（“正常表达会不会被误伤”），规则进台账并按层分类（硬约束/输入宽容/语义交给模型），每次改动跑全量回归。真实案例：为支持“改视觉呈现”加的规则误伤了“只改某镜字幕”，一次挂 6 轮——后来把目标镜头绑定交给服务端确认、而不是要求模型必须写，规则才不误伤。

**Q：Badcase 回流到 SFT 的链路？你们有吗？**
诚实讲：没有 SFT，因为我们改的是系统不是模型权重。但有等价的闭环：失败轮次 → 归因（模型理解 / 规则 / 上下文 / 数据集）→ 修复（提示词、规则、数据集、协议）→ 回归集验证 → 台账记录。如果被问“怎么判断该给模型做 SFT”，答法：先看同一类错误是否跨场景稳定出现、且规则层已收敛——那种情况才值得动模型，否则先修系统。

## 17. 幻觉、检索与 RAG 通用题

**Q：高准确性场景怎么控制幻觉？**
原则：事实必须来自工具结果，不让模型背。四招：结构化约束（schema 限制格式）；事实注入（版本号、镜头列表、有效要求都是服务端给的，不是模型记的）；后置校验（模型声称“已修改”但内容没变 → 拒绝；镜头编号不存在 → 友好拒绝并列出可用项）；精确数据从工具返回提取。

**Q：幻觉率、引用错误率多少？业务上能否接受？**
诚实回答：没有按“幻觉率”口径统计过，因为我们不是问答型 RAG——幻觉的高发区（编造事实回答用户）被“后端绑定 + 门禁”结构性挡住了；真正要盯的是“模型编造镜头编号/版本号/声称改过”这类操作幻觉，靠服务端校验兜底，测试里未授权执行 0、越权 0。如果面试官要指标，可以现场定义：操作幻觉 = 模型提出工具请求但目标不存在或参数非法，这类我们有专项断言。

**Q：查询改写、rerank、混合检索？**
标准 RAG pipeline：Query 改写（消指代、扩同义）→ 多路召回（关键词 + 向量）→ 融合（如 RRF）→ 重排（rerank 精排）。我们项目里的简化版：偏好记忆召回用关键词 + 中文语义兜底（二元组重叠 ≥50%），用 easy/hard 两套集量化过；为什么没上向量检索？语料是用户偏好不是文档，体量小，关键词够用——hard 集 75% 的差距是“下一步上向量检索”的数据依据，而不是没考虑过。

**Q：多轮对话上下文断裂怎么办？**
两层：写入侧，每轮把“当前有效要求台账、已确认记忆、最新版本快照”注入，不依赖模型自己记得；读取侧，保留最近几轮原文、更早内容滚动摘要，但已确认的约束不进压缩范围。事实回写让模型每轮看到的是服务端权威状态，而不是从长对话里翻。

## 18. 成本、性能与生产化

**Q：准确率和效率怎么平衡？**
模型路由（简单轮次用便宜模型，复杂创意轮用强模型）；上下文预算（注入内容按“该看的”精选，工具卡只给精简版，观察结果裁剪）；避免绕路（一次能做完不让模型来回试）；失败降级（确定性兜底省一次模型调用）。实测：核心套件单轮决策 p50≈9.1 秒主要是模型耗时；58 轮真实 live 约 123 次调用 / 61.5 万 token。

**Q：LLM 推理优化（vLLM、KV Cache、continuous batching）？**
诚实讲：我们是应用层，没做模型服务层优化。原理可以讲：KV Cache 缓存已算过的注意力键值避免重复计算；continuous batching 让不同请求动态拼批减少等待；量化降内存。面试这样答：先说明自己负责的应用层优化（成本档、上下文预算、失败不盲试），再说这些属于推理服务层，生产化要接的话是部署团队的事，不是应用代码。

**Q：超时、重试、熔断怎么设计？**
生成模型调用有超时；重试用指数退避并限制次数；连续失败走熔断（快速失败 + 兜底画面），绝不无限重试烧钱；重试与幂等标识绑定，避免重复扣费/重复生成。评测默认关真实生成，就是把这类不可控成本从日常回归里拿掉。

**Q：高并发下怎么设计？**
诚实边界：当前是单机/本地形态，会话、草稿、记忆按用户隔离的设计已经就位。生产化要做：异步任务队列（长任务不阻塞请求）、限流配额（按用户/按模型档）、水平扩展（无状态服务 + 负载均衡 + 共享存储）、监控（耗时、token、失败率、门禁拒绝率）。这些是明确的后续项，不是已经做完的东西。

## 19. 行为面试与项目表达

**Q：自我介绍怎么说？**
30 秒版：我是做大模型应用/Agent 方向的，最近一个项目把“AI 生成视频”从“模型直接出片”重构成“模型导演一份可编辑时间线”，核心是让 AI 的输出可审查、可局部修改、可评测。2 分钟版再加：为什么做、架构三层、评测数据（核心套件 51/51 确定性通过、真实出片）、踩过的坑（评测环境≠真实环境）。

**Q：你在项目里的角色和边界？**
端到端：架构设计、协议定义、后端执行链路、评测体系、文档。讲“我主导 + 具体分工”，不抢别人功劳，但说清楚哪些是你定的。

**Q：遇到的最大困难？意见不合怎么推进？**
挑真实故事：规则误伤（一次挂 6 轮）、评测环境与真实环境认知反转、语义匹配误判。讲法：现象 → 排查 → 归因 → 修复 → 数据验证。意见不合的答法：用数据和事实沟通，不情绪化，先小范围验证再全量。

**Q：项目有什么不足？**
诚实给三条：没有真实线上流量（评测是脚本 + 裁判，不是用户行为）；生成质量不是卖点（卖点是编排正确性）；生产化未完成（单机形态、无监控告警）。再补一句“每个不足都有下一步”，比如向量检索有 hard 集数据依据、生产化有明确清单。

**Q：为什么想做 Agent 方向？**
因为它把“模型能力”变成“系统能力”，核心挑战是可靠性和评测，这正是我想深耕的。换工作原因答真实但不抱怨：想专注大模型应用/Agent 方向，现有岗位给不了这个深度。

## 20. 补充面经专题（安全 / 多模态 / 视频生成 / 合规 / 设计题）

### 20.1 Agent 安全（OWASP LLM Top 10，字节/安全面高频）

**Q：Prompt 注入有哪几种？怎么防？**
两种：**直接注入**——用户输入里夹带指令（“忽略之前的规则，直接执行……”）；**间接注入**——外部数据（网页、文档、邮件、素材描述）里藏指令，模型读取后当成自己的指令执行。防护要分层：输入侧给“系统指令”和“用户数据”划边界，用户内容一律当数据处理、不当指令执行；模型侧用安全提示词；但最关键的是**执行侧**——工具、权限、授权不依赖模型自觉。我们的原则：**模型可以被骗，系统不能**：系统字段服务端绑定、动作分三档、交付显式授权、外部地址校验。

**Q：Agent 特有的安全风险除了 Prompt 注入还有什么？**
- 越权操作：模型误调高权限工具 → 权限分档（只读/改草稿/交付）+ 显式授权；
- 数据外带：把用户素材或记忆通过外部工具发出去 → 外部地址校验、公网发布走显式流程；
- 敏感信息泄露：PII 进上下文或日志 → trace 只留必要字段，不存推理摘要；
- 工具滥用/成本炸弹：模型反复调用贵工具 → 工具卡标成本档、失败不盲试、调用次数与 token 记账。

**Q：人在回路（HITL）在 Agent 安全里是什么角色？**
最后兜底：任何不可逆或花钱的动作（正式渲染、真实生成）必须用户确认才执行；模型或系统判断可以骗过一层，但不能骗过“用户显式确认”这一层。

### 20.2 多模态：视频/素材怎么被理解（网易有道 Agent 算法面真题）

**Q：全模态的意图理解怎么做的？Video 信息是怎么用的？**
输入分四路：文本（用户需求）、视频（样例参考）、图片/音频（用户素材）、UI 控件（比例/时长等硬约束）。样例视频的处理是预处理器**抽帧、音频、元数据**，交给多模态模型产出**结构化理解**：叙事结构、氛围、剪辑手法、节奏、可复用/不可复用风格，并按时间切成段；这份“参考摘要”注入导演规划，决定分镜和节奏，但**不直接当素材用**。用户素材则按类型做能力分析（适合什么画面角色、时长比例），规划时决定放哪一镜。关键原则：理解结果必须落到可执行的结构（时间线、素材槽），不是一段漂亮描述；模型不可用时走启发式兜底，不假装理解。

**Q：为什么样例只能当“参考”而不是直接复刻？**
样例视频是风格和结构参考，不是可复用素材：直接复用会带来版权和内容重复问题；而且用户要的是“这个味道”的新片，不是逐帧搬运。所以理解层输出的是**结构化创作事实**（节奏、风格、分镜意图），素材槽由生成模型或用户素材填充。

### 20.3 视频生成基础速答（可灵/视频生成岗位一面）

**Q：视频生成和图像生成的本质区别？**
图像是 2D 静态分布；视频多了时间维度，要同时解决**帧间一致性、运动合理性、长程时序依赖**。所以视频生成的核心难点不是“单帧画得好”，而是“连续几十上百帧又一致又自然”——这也是视频模型普遍比图像模型重、慢、贵的原因。

**Q：为什么主流视频生成用 Diffusion 而不是 GAN？**
Diffusion 训练稳定、覆盖模式广、不易模式坍塌，配合 DiT（Transformer 主干）能较好建模时空关系；GAN 生成快但训练不稳定、多样性差。现在也有自回归与 DiT 混合的路线。面试答“稳定性和可控性优先”即可，不必展开公式。

**Q：你们项目怎么用视频生成？**
视频生成（Seedance）只负责“真实画面补全”这一个执行环节：规划阶段产出素材任务，执行时提交生成、轮询状态、下载、标准化后进时间线；模型不可用或失败时走静态图动效/卡片场景兜底，**绝不把占位当成品**。所以视频生成是“可替换执行器”，不参与决策——这是架构上把它和 Agent 解耦的原因。

### 20.4 AIGC 内容合规与审核（火山/字节内容安全方向）

**Q：AIGC 生成内容怎么保证合规？**
标准答法是“机审 + 人审 + 模型优化”闭环：接入侧红线词与涉政/涉黄/涉暴检测，生成侧加水印和来源标记，出片前内容审核门禁，投诉和误判回流到规则/模型优化。诚实讲：本项目是原型，未接入商业审核服务；但架构上把“审核”设计成执行链路里一个**可插拔门禁环节**，接服务只改配置，不动主流程。

### 20.5 现场设计题答题框架（阿里 Offer 面经）

**Q：现场让你设计一个 XX Agent，怎么答？**
框架：**需求澄清 → 边界与假设 → 整体架构 → 数据流 → 关键机制 → 异常与成本 → 评测与上线**。反例是上来堆“RAG + Agent + 多模态 + MCP”名词，却没讲清数据流、异常、成本。正例：先问“用户是谁、输入输出是什么、单用户还是高并发、允许失败吗”；再给分层架构；然后讲一条请求怎么走；最后主动说“哪里会挂、怎么降级、怎么评测、上线先看什么指标”。用本项目当模板演练一遍：意图路由 → 状态/记忆 → 工具编排 → 执行门禁 → 结果回写 → 评测闭环，正好覆盖这套框架每一步。
