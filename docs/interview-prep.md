# 面试准备：可编辑时间线的 AI 视频导演 Agent

> 用法：正文（§0–§20）是面试答案，全部用人话写，不出现内部函数名/事件名；附录是内部名词对照表，只给自己对照代码用，面试别念。涉及指标时以对应评测报告为准；涉及架构时以当前 V2 代码为准，不把历史实现或生产化方案说成已落地能力。

## 0. 一句话定位

我不是在做“文生视频”工具，而是在做**让大模型当导演的 Agent 系统**：模型不直接出片，而是产出**一份可审查、可修改、可版本化的视频方案**，再编排外部能力（生成模型、视频处理、渲染器）把它做成成片。生成模型只是可替换的执行器之一。系统还保存创作记忆，用于在后续规划中按作用域复用用户偏好与当前项目要求；是否“越用越懂”应由真实用户或 live 评测验证，当前不作效果承诺。

### 0.1 版本与简历口径

项目经历过一次协议与执行链路收敛。早期“样例迁移/旧渲染协议/兼容状态包”属于历史阶段；当前 V2 的唯一可执行真相是统一时间线方案，围绕“草稿 → 修订 → 渲染运行”工作。面试中必须把**历史实现、当前 V2、生产化设计**分开说。

**Q：简历里写过旧协议、任务队列或实时推送，为什么当前代码不同？**

先主动校准事实：旧协议和兼容状态只服务历史数据或旧界面，当前 V2 已收敛到统一时间线协议。当前桌面 V2 先用同步 API 跑通版本化渲染闭环；导演对话使用 SSE 推送。若简历中的队列化/双向实时推送确实来自旧版本，应明确说“历史实现”；若只是做过设计或验证，应说“生产化方案”，不能说成当前已上线能力。这样回答的重点不是辩解，而是说明收敛的原因：减少多份状态真相、先验证可编辑与可追溯，再做分布式扩展。

### 0.2 为什么从旧版迁到当前 V2

**Q：为什么要把 MigrationProtocolV12、PipelineBundle、RenderPlanV1 换成当前的时间线工程？**

这不是为了“换协议名”，而是把活动主路径的核心对象从“样片理解 + 派生计划”换成“可编辑时间线工程”。MigrationProtocolV12 的职责是把样片理解成语义锚点和复刻指令；PipelineBundle 同时装着理解结果、由它派生的时间线/大纲、素材、任务状态和可选渲染计划；RenderPlanV1 再负责渲染执行。也就是说，同一个创作意图会在“理解结果、派生时间线、已保存的渲染计划”里有多种表示。代码能证明这些表示并存，不能单独证明它们已在生产中造成了冲突。

旧 V2 的渲染路径是“主视频 + 透明特效层 + FFmpeg 叠加”；当前 V2 则使用由 Remotion 直接消费的统一时间线规格，预览负责生成、校验、审查并保存草稿，正式运行消费指定修订完成素材补全、标准化和时间线渲染。这是代码和重构文档可复核的变化。不要把“旧方案一定无法支持多镜头”说成已验证结论；它是本次架构选择没有继续沿用的路径。

**Q：为什么不在旧链路上继续打补丁？迁移怎么控制风险？**

代码可确认的是：旧包同时携带理解结果、派生时间线/大纲和可选渲染计划；当前 V2 预览/运行主路径独立，旧包只用于既有界面的兼容读取，旧 V2 overlay-first 链路及相关推送、trace 已被清理。没有可复核的 ADR 能证明“继续打补丁一定会失败”；面试时应把它说成一次主动收敛：避免长期维护两套活动写入路径，并让旧状态不反向改写 V2 的权威时间线。

**Q：改完后的效果怎么样？有证据吗？**

分两层回答。能力上，当前已经能把编辑保存为不可变修订，并让每次渲染独立绑定一个修订和方案快照，因此重渲染不会覆盖旧产物；这解决的是可编辑性和可追溯性。验证上，最新可复核的 2026-08-09 deterministic-only 报告（代码 `1efc746`）中，6 个 Remotion 场景的交付成功率为 100%。但这只证明确定性的素材解析、标准化和渲染工程链路；真实生成视频的审美质量、线上时延、用户满意度和 live Agent 指标均未在该报告中运行或统计，不能把它包装成业务效果。

### 0.3 为什么不再使用 BullMQ、Redis 与任务 WebSocket

**Q：简历中的“BullMQ + Redis 拆分理解/渲染任务，WebSocket 推进度”是真做过，还是设计？**

这是历史服务端形态，不能说成当前 V2 的运行方式。历史代码里有分析与生成两个 Worker：任务先入队，Worker 分别处理视频理解和生成/渲染；Redis 保存队列状态，WebSocket 按任务推送阶段和进度。要补充一个容易被追问的细节：当时的桌面本地模式已经可以把同一套任务处理逻辑放在进程内执行，并非所有环境都必须启动 Redis 和 Worker。因此简历更准确的表述是“历史服务端模式实现过异步任务闭环”，而不是“当前系统依赖 BullMQ”。

**Q：到底为什么从 BullMQ 任务链路切到当前 V2？**

按现有代码能证实的事实回答：这次重构的重心从旧版“任务创建 → 后台分析/生成 → 任务进度”的服务端工作流，切到了“预览草稿 → 保存修订 → 渲染指定修订”的可编辑工作台。当前桌面主路径明确不依赖 Redis、外部队列或独立 Worker，渲染由 V2 API 在请求内完成。旧的任务服务、Worker 和任务 WebSocket 已不再属于活动 V2 路径。

没有可复核的 ADR、提交说明或指标表明“BullMQ 性能不行”或“旧队列已经造成串版，所以必须删除”。因此最诚实的说法是：**产品和实现阶段换了重心，当前先交付和验证桌面端的可编辑时间线闭环，异步调度暂时不在活动主路径的范围内。**不要把这个阶段性取舍包装成队列技术本身有缺陷或已经获得某项性能收益。

V2 的修订和 RenderRun 确实已保存源 revision 与方案快照，现有 smoke 也断言不同 revision 的 RenderRun 能共存；这说明将来改回异步时有了更明确的执行对象。但当前没有 V2 队列 Worker，也没有异步重试/并发编辑回归，不能说“异步不串版已被当前系统验证”。

**Q：当初为什么选异步队列 + WebSocket？新版不也是先规划再出片吗？**

两者都有产品层面的“先规划、再出片”，区别是**执行协议**。旧版提交分析/生成后，HTTP 立即返回任务 ID 和排队状态，后台 Worker 继续处理，页面通过 WebSocket 等待后续进度和结果；因此需要队列。新版先通过预览生成并保存可编辑草稿，用户确认或修订后再请求渲染；但当前渲染请求会在服务端等待指定修订跑完后直接返回结果，并不是“受理后立刻返回、后台异步执行”的任务接口。视频理解、外部生成和 Remotion 渲染都可能耗时且失败，旧版队列正是为这类服务端长任务准备的：它解耦 API 和执行，方便独立扩 Worker、重试和取消，WebSocket 则让页面不必轮询就能看到进度。

**Q：现在为什么不用了？是不是技术倒退？**

不要争辩“同步比队列先进”。当前不是生产级长任务架构，而是桌面/原型的活动路径选择：少启动 Redis、Worker 和长连接，直接验证编辑器、时间线协议和成片编排。它的代价很明确——同步请求会占住连接，进程重启后难恢复，也不适合高并发、可靠取消和多机扩展。若面试官问生产化，你应回答“当前尚未接回队列；需要时会以指定 revision/RenderRun 为 Job 输入重新设计”，而不是说已经完成。

**Q：这是“服务端项目改成桌面端项目”吗？两者有什么区别？**

不能这样绝对地说。历史代码已经同时支持两种运行形态：服务端模式启动 API、PostgreSQL、Redis 和独立 Worker；桌面本地模式则使用本地文件存储，并在应用进程内处理任务。更准确的表述是：**从兼容服务端/桌面端的旧任务框架，收敛为 desktop-first 的 V2 主路径。**

桌面端不等于“没有后端”：Electron 仍会在本机启动后端 API、前端和 Remotion/FFmpeg，只是它们服务于当前电脑上的一个创作工作台，不要求独立的数据库服务、Redis 或 Worker 集群。原因是**当前 V2 被定义为 desktop-first 本地运行路径**，而不是因为“数据量小”——仓库没有容量基准或数据量阈值可以支持后者。服务端模式面向远程、多用户和横向扩展，才需要共享存储、持久队列、鉴权、限流和运维监控。当前选择前者，是为了让本地创作工作台无需额外基础设施即可运行，并把实现重点放在可编辑时间线；这不代表已经具备后者的生产能力。调用外部视频生成模型时仍可能联网，桌面端也不是完全离线。

**Q：WebSocket 被什么替代了？**

不要笼统回答“都换成 SSE”。当前导演对话确实用 SSE 输出本轮过程和工具进度；但编辑器直接发起的 V2 预览、保存和渲染走普通 REST，渲染会等待当前版本完成后返回，并没有通用的后台任务进度流。这样说比把 SSE 包装成完整的实时渲染系统更准确。

**Q：以后恢复异步渲染，怎么接回去才不破坏 V2？**

把“渲染某个不可变修订”作为唯一 Job，而不是把前端传来的整份可变方案或裸 taskId 塞进队列。API 先持久化草稿修订和运行记录，再通过 Outbox 可靠入队；Worker 以 Job 幂等键执行素材生成、标准化和 Remotion，状态和供应商任务号都落库；进度按运行记录推给 SSE 或 WebSocket。这样失败可重试、重复投递不重复扣费、断线可恢复，而且旧任务不能覆盖新修订。到真实长任务和并发量出现前，这只是生产化设计，不能说已实现。

## 1. 三分钟讲法

1. **背景**：早期版本围绕“样例视频迁移”和任务式生成组织，历史代码也有渲染计划编辑接口。V2 重构把主流程收敛为“导演编排 + 可编辑时间线”，而不是宣称旧版完全不能编辑。
2. **核心机制**：一份视频方案被拆成三层——**草稿**（正在编辑）、**修订**（每次改动留下的不可变快照）、**渲染**（针对某个版本执行一次出片）。局部修订只允许修改协议授权的范围，范围外字段从旧版保留；只有用户明确要求整体重写时，才允许全局改动。第二次渲染不会覆盖第一次的产物。所有执行、校验、存档都收在服务端一处；前端负责编辑和展示，但不拥有权威写入或执行判定。
3. **工程方法**：审查分三类（硬约束严格、输入宽容、语义交给模型判断）；评测分离线自检、真实模型回归和真实出片三层。失败归因、反例测试和全量回归是本项目采用的开发约定，不应说成系统自动强制了“每一次失败/每一次改动”。指标只报带日期和提交版本的评测报告；当前最新正式产物是 deterministic-only，不把历史 live 指标当作现状。
4. **一句话总结**：把“大模型出片”变成“大模型编排一份可追溯、可二次修改的视频方案”，这是它和普通 AIGC 的本质区别。

## 2. 项目背景类

**Q：解决什么问题？**
早期是“样例迁移 + 任务式生成”，并保留了渲染计划编辑能力；当前 V2 改为“导演对话 → 结构化方案 → 局部修改 → 版本化渲染”。V2 的草稿、修订和渲染运行可追溯；不要把历史版本概括成“完全不可编辑”或断言前后端曾发生过具体状态不一致，除非你有对应 issue/trace。

**Q：规模？**
一个仓库六个部分：前端、后端、前后端共享的协议、渲染工程、桌面壳、评测数据集。核心逻辑在“导演服务”和“执行管线”两块。

**Q：技术栈？**
TypeScript 全栈（前后端共享类型定义，部分协议问题可在编译期暴露），前端 React，后端 Express；桌面本地路径使用文件存储，仓库也保留 Prisma/关系型数据库的服务端路径。渲染使用 Remotion，视频处理使用 FFmpeg，画面生成通过可替换 Provider 适配器接入。

**Q：这个项目做得好不好，有数据吗？**
可以报，但必须先拿到对应报告并带上日期、代码版本和运行模式。当前可复核的是 2026-08-09 的 deterministic-only 报告（提交 `1efc746`，报告注明工作区有未提交改动）：确定性冒烟通过，6 个 Remotion 场景交付成功率为 100%；live Agent 与裁判模型指标为 N/A。因此不要把历史的 51/51、92.2% 或时延数字说成当前结论。口径上，确定性检查是程序断言（动作、工具、状态、版本是否正确），回复质量才应由独立裁判或人工抽检评价。

## 3. 架构类

### 3.0 面试前必背：当前架构事实清单

这组事实应先说清，再展开具体技术细节：

- **当前协议**：活跃的视频工程协议是 `RemotionTimelineSpecV1`。其中 `V1` 是协议 schema 版本，`V2` 是当前工作流名称；二者不是新旧系统的关系。已有草稿的“基线方案”是上一修订的同一份协议快照。
- **权威状态**：后端保存草稿（最新可编辑状态）、修订（不可变快照）和 RenderRun（绑定来源修订与来源方案快照的一次出片）。前端只发请求和展示结果，不拥有版本或执行的最终写权。
- **角色不是固定数量**：普通视频规划链路是 Director → LLM Planner → 只读 Timeline Outcome Reviewer；预置效果不够时，才额外调用 Component Authoring Agent。组件 Agent 内部还会做试渲染与视觉验收。面试中应说明“一个编排 Agent + 受控专业模型模块”，不要脱离统计口径只报固定的两个、三个或四个 Agent。
- **修改链路**：Dispatcher 绑定用户、草稿、修订和目标 ID 后，Planner 生成候选完整协议；服务端按授权 scope 用基线方案回填范围外内容，再交 Reviewer 做语义审查，最后经过结构、组件引用和零差异/提交门禁才写入新修订。
- **通信与运行边界**：Director 对话向前端用 SSE 推进度；编辑器预览、保存、渲染走同步 REST。当前 V2 不接 BullMQ、Redis Worker 或 WebSocket；桌面端仍会启动本地后端与渲染进程，并非纯浏览器离线执行。

**Q：整体分层？**
三层：
- **输入展示层**（前端）：收用户的自然语言和素材，展示导演对话事件、草稿和渲染结果；可以提交编辑/预览/渲染请求，但不自行做权威写入、校验或执行判定。
- **决策调度层**（后端上半）：理解意图、维护“当前项目要求”和“长期偏好”、决定这一轮要调用哪个能力。
- **执行管线层**（后端下半）：规划方案、按范围修改、解析素材、标准化、渲染出片、留证据。
三层之间靠一份**统一的时间线协议**衔接：前端展示、后端校验、渲染器读取的都是同一份结构。

**Q：一条请求怎么走？**
导演对话时：前端发起 HTTP 请求并接收 SSE 事件 → 后端恢复本次会话、注入有效要求和相关记忆 → Director 产出结构化 Skill/Tool 提议 → Dispatcher 校验工具、权限和系统绑定字段。

若是规划/修订：Dispatcher 组装含当前草稿和目标范围的 `V2PlannerInput` → LLM Planner 生成候选 `RemotionTimelineSpecV1` → 服务端先按 scope 合并为实际可保存的候选 → Timeline Outcome Reviewer 仅返回 `pass / violations / repairInstruction` → 不通过时 Planner 只带审查意见再修正一次 → 结构校验、组件引用校验和修订提交门禁通过后，后端保存新修订。若必须新建特效，`render.author` 先生成并验收组件，后续规划工具必须显式依赖该结果才可引用组件 ID。

编辑器单独点击预览、保存、渲染时走普通 REST：预览和保存直接返回，渲染请求会等待指定修订完成后再返回结果。

**Q：为什么执行权必须在服务端？**
因为“谁执行、改了什么、存成哪个版本”必须是**唯一事实**。前端可以发起请求和维护交互状态，但如果由前端决定版本、权限或实际执行，就会出现同一操作两端跑、状态对不上的问题。服务端是唯一权威，出了任何问题都只查一个地方。

**Q：三个核心实体？**
- 草稿：你正在编辑的当前版本。
- 修订：每次改动保存下来的**不可变快照**，旧版永远在，随时能回看“第几版改了什么”。
- 渲染：针对某个具体修订执行一次出片，记录“基于哪个版本、用了哪份方案”。

**Q：二次渲染会不会把第一次的结果删掉？**
不会。每次渲染是独立记录，记录中固化来源修订和来源方案快照；第二次渲染基于新修订创建新记录，第一次的产物不会被后一次运行覆盖。具体“跑过几条、文件多大”只在有对应产物和报告时再说。

## 4. 核心设计决策

### 4.1 审查三分法
- **硬约束**：版本、范围和零差异由程序校验；正式渲染目前还有本轮意图门禁，但独立的用户确认令牌尚未实现。前几类适合严格校验，语义是否满足创作要求则不能只靠死规则。
- **输入校验**：模型传的参数合不合法——这类**宽容**，允许模型用自然方式表达，只拦会破坏状态或越权的输入。
- **语义判断**：改得对不对、回答切不切题——这类**不写死规则**，交给另一个模型当裁判，或用语义匹配兜底。

如要讲“规则误伤正常表达”的故事，必须确认这是你亲历且能说明修复与验证的案例；代码本身只能证明目标、范围和零差异存在校验，不能证明某一线上事故发生过。可提炼的工程原则是：**输入尽量宽容，状态变更保持严格**；反例测试和回归是开发约定，不是当前服务端自动强制流程。

### 4.2 按范围修改
用户说“只改第二镜的转场”，系统只允许协议授权的那一块变化；范围外字段从旧版保留。如果模型最终其实什么都没改，系统也会拒绝保存（防“假装改过了”）。当前有六类范围：字幕、单镜头内容、连续镜头结构调整、单镜头视觉呈现、指定转场、全片总纲或整体重写；整体重写只在用户明确要求推翻整案时使用。

### 4.3 目标场景由服务端确认
模型给的“镜头编号”不应直接信任。所以系统会拿它和当前方案的真实镜头对照：对得上才用，对不上就拒绝并返回可用目标；用户未指定目标时，才使用当前编辑上下文中的选中镜头。**身份由系统绑定，不信任模型字符串。**不要补充“真实模型已经编造过编号”，除非你有可展示的 trace。

### 4.4 记忆分两级（创作知识沉淀）
- **长期偏好**（跨项目）：“我做的片子都偏蓝灰低饱和”——作为用户级记忆保存，并在后续相关规划中参与召回；用户能查看、撤销、删除。
- **当前项目要求**（单项目）：“这一版旁白要冷静克制”——只对这一部生效，是“这单的合同”。

保护机制：每条记忆都有**作用域**（用户级/草稿级）和**状态**（生效/候选/已撤销）；模型推断或不确定的偏好只能作为**候选**，不直接控制创作；用户明确要求记录的稳定偏好可生效；撤销过的同项偏好再次出现会回到候选，不能静默复活。用户可查看、撤销或删除。

使用方式：Director 规划路径会按作用域**召回**相关记忆并注入上下文；只有 active 记忆会传给时间线规划，candidate 仅作为待确认信息。写入、召回、失效有来源字段并写入相关 trace；具体检索质量只引用带版本的评测报告。

### 4.5 渲染绑定版本
每次渲染记录“基于第几版、用了哪份方案快照”。第二次渲染用新修订，第一次的产物与记录原样保留。这是“可编辑时间线”能成立的关键：方案可改、版本可溯、渲染可重复而不互相破坏。

### 4.6 留证据（可观测性）
Director 对话与 V2 预览/渲染路径会写 trace；其中保存输入、模型调用审计、工具结果、规划/渲染产物等内容，具体文件随路径而异。它支持按目录回看一次操作，但目前没有脱敏、访问控制和保留期治理；不要概括成“所有环节、所有细节都已可回放”。

### 4.7 评测体系
- 第一层**离线自检**：不花钱、不动模型，验证协议、边界、版本正确性；仓库有多组确定性 smoke/回归脚本。是否每次改动都完整执行，取决于实际开发流程与本次报告，不能由代码自动证明。
- 第二层**真实模型评测**：让真模型按多轮场景对话，看它会不会选对工具、改对范围、记对要求、正确地拒绝不该做的。报告应区分 deterministic smoke、live Agent、裁判模型和真实出片，不能把未运行的 live 指标补成 100%。
- 第三层**真实出片**：真正调生成模型、视频处理、渲染器，产出可播放的 MP4。

仓库中有回归台账和针对门禁的确定性用例；后端也会对多类拒绝返回原因。将失败登记、反例测试和全量回归作为开发流程是合理做法，但没有代码证据表明每次失败都会自动入账，或已完全消除规则遗漏。

## 5. 高频技术问题（人话）

**Q：当前哪些链路使用 SSE，哪些不是？**
导演对话接口使用 SSE：前端发一个普通 HTTP 请求，后端不立刻返回，而是把这一轮进展像直播一样一小条一小条推回来，连接保持到本轮结束。事件按**角色**分四类：
1. 过程提示：展示“正在理解、正在检查”这类状态；
2. 执行进度：选中了哪个能力、开始做什么、进度多少、成功还是失败；
3. 最终结果：给用户看的回复；
4. 状态同步：每轮结束把服务端权威的会话状态推给前端刷新界面。

编辑器直接发起的预览、保存和渲染不是队列任务流：它们走 REST；当前渲染请求等待完成后再返回，前端只展示本地阶段提示。因此不要笼统地说“所有视频任务都由 SSE 实时推送”。

**Q：为什么不用 WebSocket？**
当前导演对话是服务器单向事件推送，SSE 足够且可复用同一条 HTTP 请求的身份边界与错误处理；当前 V2 也没有 WebSocket 服务。若未来改成多用户协作编辑、客户端取消/控制任务，或队列 Worker 持续上报长任务进度，再评估 WebSocket；单向任务进度仍可继续用 SSE。

**Q：重复提交怎么防？**
先区分三个概念：**幂等**是同一业务请求重试多次只产生一次副作用，并返回同一业务结果；**去重**是发现重复后拒绝；**乐观并发控制**是旧版本写入时返回冲突。后两者都很有用，但不等于前者。

当前是**渲染链路已具备请求级幂等，其他写路径仍是局部去重与版本保护**，不能笼统说“全链路幂等已完成”：

- Director 工具调用用“会话 ID + `turnRequestId` + 序号”生成稳定 `callId`；已经完成并写入会话近期列表的同一调用会被拒绝。它是顺序重复调用保护，重复请求得到的是拒绝，不是第一次结果的回放。
- 这个工具级检查发生在执行前，而 `recentToolCallIds` 在一次调度返回后才写入工作区；代码没有 in-flight 记录或互斥锁。因此两份相同请求同时到达时，不能承诺只会执行一份。`turnRequestId` 目前也没有作为整轮 Director 对话的结果回放键：网络重试仍可能再次调用 Director、写状态或提出不同工具方案。
- 草稿保存要求 `baseRevision` 匹配，并用条件更新防止旧版本静默覆盖新版本。这是乐观并发控制，不是幂等；第二次保存会得到版本冲突。
- 旧的公开 preview 写入口已经移除；创建与修订统一经过 `/api/director/chat` 的摘要/修改确认和整轮幂等边界，不能绕过确认直接调用 Planner。
- `POST /api/v2/timeline-drafts/:draftId/runs` 已要求 `Idempotency-Key`（长度不超过 200）。服务端以 `userId + operation + idempotencyKey` 唯一保存 receipt，并同时保存 draft、revision 的请求 hash、运行状态、RenderRun 和可用时的 Provider task ID。相同 key、相同请求：运行中返回同一运行；完成后回放同一 RenderRun；失败后返回同一失败。相同 key 却指向不同草稿/修订会报 409。单进程内还用 in-flight map 合并并发请求；前端一次网络重试也会复用本次调用生成的 key。换一个新 key 才表示用户有意重新渲染同一修订。
- 素材生成在渲染链路内也会用“渲染 key + material job ID”派生 receipt，并在 Provider 返回任务号后写入 `providerTaskId`。但 Provider 提交请求本身没有看到幂等键透传；如果外部服务已经受理、而本次提交响应在任务号返回前丢失，当前代码不能靠 Provider 侧查询彻底消除“不知道是否已受理”的歧义。组件创作和草稿预览/保存也没有同等的请求结果回放。
- 上传按文件内容哈希复用已有文件；创作记忆创建会按同用户、作用域和归一化文本复用现存未撤销记录。这两者是业务去重，仍不能替代并发安全的请求幂等。

生产化应由客户端提交幂等键，服务端以“调用方 + 操作类型 + 资源标识 + 幂等键”建唯一记录，并保存请求指纹、`running/completed/failed` 状态和最终结果引用：首个请求原子创建 running 记录；相同键且相同指纹的重复请求返回同一运行记录/结果；相同键但请求体不同则报冲突；执行完成后保存结果。外部生成 Provider 也要透传该键或先持久化其 task ID。注意不要只把 `(draftId, revision)` 设为唯一：用户可能有意对同一修订再出一版片，只有**复用同一幂等键**才表示网络重试，换新键才表示新的渲染意图。

**Q：哪些机制真正需要做幂等？优先级怎么排？**

先给所有**会花钱、创建不可逆资源、推进版本或写用户状态**的入口加；纯读取、校验和确定性计算不需要。当前项目建议的优先级如下：

| 优先级 | 操作 | 当前风险 | 建议幂等边界 |
|---|---|---|---|
| 已覆盖（仍有外部边界缺口） | `POST /api/v2/timeline-drafts/:draftId/runs` | 同 key 的网络重试已能复用 receipt/RenderRun；但进程崩溃后的 running receipt 尚无独立恢复调度 | 保留 `userId + operation + Idempotency-Key` 唯一约束；增加恢复器/队列消费者处理长期 running receipt |
| P0 | 外部视频生成提交 | 内部已按 `render key + material job ID` 持久化 receipt 与已返回的 Provider task ID；但提交响应丢失在 task ID 返回前仍有歧义 | 将 `renderRunId + materialJobId` 透传为 Provider 幂等键，或用 Provider 支持的查询键恢复提交状态 |
| P1 | `POST /api/director/chat` | 同一轮网络重试可再次调用模型、写要求/记忆、发起工具 | `workspaceSessionId + turnRequestId`；保存整轮 receipt 与状态事件，重复请求回放或附着到同一轮 |
| P1 | `PUT /api/v2/timeline-drafts/:draftId` | 响应丢失后客户端不知道是否已保存，只能收到版本冲突 | `userId + draftId + baseRevision + Idempotency-Key`；保留乐观锁，同时回放首次成功的新 revision |
| P1 | `render.author` | 重试会再次调用代码模型、试渲染并可能留下多份组件尝试 | 绑定到 Director 的 `callId`/客户端幂等键；同键返回同一组件结果或失败结果 |
| P2 | 创作记忆创建/替换 | 顺序重复已有文本会复用，但并发仍缺少数据库唯一约束 | 以用户、scope、draft、归一化 statement 或请求键建唯一约束；替换操作记录来源动作 |
| 已部分覆盖 | 上传 | 已按内容哈希复用文件 | 保留内容哈希；若上传存储改为远程对象存储，再增加上传会话/分片完成幂等 |

删除的目标状态天然趋向幂等：同一资源删两次的最终状态都是“不存在”。当前接口第二次会返回 404；若生产客户端需要无歧义重试，可把“已删除”也规范成成功结果或按删除 receipt 回放。读取、协议校验和 scope 合并本身不需要请求幂等；渲染器虽可基于不可变输入确定性执行，但外层渲染 API 会创建产物、消耗资源并可能调用 Provider，必须承担请求幂等。

**Q：幂等记录怎么实现，避免只是加一个 Header？**

渲染路径现在已有 `V2IdempotencyReceipt`：调用方、操作类型、草稿/资源标识、客户端 key、请求体 hash、`running/completed/failed`、阶段、RenderRun 和 Provider task ID。数据库 schema 对 `userId + operation + idempotencyKey` 有唯一约束；本地文件仓储也模拟了相同约束。其余写操作若要补齐，可复用这个模式：

1. 首个请求插入 `running` receipt 后才执行实际副作用；
2. 同 key + 同 hash：若仍在执行，返回同一 run/轮次的状态；若已完成，回放首次结果；
3. 同 key + 不同 hash：返回 409，防止客户端错误复用 key；
4. 执行完成后，将 RenderRun、草稿 revision 或 Provider task ID 写回 receipt；
5. 未来接回队列时，Worker 也以同一 receipt/唯一键领取任务，不能只依赖 BullMQ 的“至少一次投递”。

这套机制解决的是“超时后到底有没有成功”的不确定性；版本冲突机制仍保留，用来解决两个不同用户意图并发修改同一草稿的问题，二者不能互相替代。

**Q：两个人同时改一个方案怎么办？**
保存修改时要求“你基于的版本必须还是当前版本”，对不上就报冲突，不会静默覆盖别人的修改。

**Q：本地和真实环境怎么切换？**
桌面本地路径使用文件存储；仓库也有 Prisma/关系型数据库路径。两者在草稿、修订等仓储接口上保持相近，但服务端部署还涉及数据库、对象存储与 Worker 等基础设施，不应简化成“只改一个配置就能完成生产切换”。

**Q：中文文本匹配怎么做？**
先把文本归一化（Unicode 归一、大小写和空白统一），再切短词（中文二元词、英文数字连续词）；排序使用 BM25 式词项分数，并给“连续中文短语包含”加分。这是轻量关键词召回，不是向量语义检索；它能缓解部分改写，hard 集表现不足正是后续引入向量检索的原因。

**Q：安全上怎么防恶意输入？**
不要把“做了校验”统称为“安全”。当前代码可分为五层：

1. **模型与动作边界**：Tool 参数是严格 Zod schema；Tool 必须由本轮选中的主 Skill 申请，依赖只能指向已完成的前序动作；`chat/clarify` 不允许执行 Tool，交付 Tool 必须是 `execute` 模式。模型不能提供 `userId`、草稿、revision 或素材选择等系统字段，Dispatcher 会从服务端上下文绑定。
2. **状态完整性与越权止损**：草稿、修订和 RenderRun 查询都按 `userId` 作用域；保存要求 `baseRevision` 条件更新，协议校验会检查 ID、时间、资产/镜头/素材任务引用；自定义组件还要校验存在性、用途匹配、draft 授权和当前画布的视觉证据。
3. **高成本动作门禁**：正式渲染必须有当前草稿、素材就绪、`execute` 意图和本轮授权判断；渲染请求要求幂等键，避免同一网络重试重复出片。这里的授权仍由本轮结构化决策和用户文本推导，**不是**独立的二次确认令牌。
4. **文件、路径与外部地址**：JSON body 限制为 10 MB，上传单文件限制为 200 MB；上传落盘使用 UUID 文件名，上传资源解析会限制在 `uploads` 目录、拒绝隐藏名和路径穿越。给外部图生视频 Provider 的 URL 分类会拒绝 `localhost`、`.local`、私网 IPv4/IPv6 字面量和非 HTTP(S) 协议；自定义 Remotion 组件采用 import 白名单，并禁用网络、存储、`eval`、动态 import、随机数和墙上时钟动画。
5. **可追溯性**：规划、模型输出和运行过程会写 trace，草稿/修订/RenderRun 形成可回溯链路；这有利于定位，不等于日志已脱敏或已具备生产审计能力。

边界也要主动说清：认证中间件只是“没有 `x-user-id` 就补为 1”的本地占位，客户端可伪造该 header；`cors()` 未限制来源，`/uploads` 与 `/v2-renders` 是公开静态目录。上传未做 MIME 魔数校验、病毒扫描或用户配额；没有限流、内容审核、敏感字段脱敏/加密/保留期限。更关键的是，样片分析的 `resolveVideoInput` 仍允许 `http(s)` 下载、`file://` 和本地路径读取，**它没有复用外部 Provider 的 URL 分类器**，所以不能声称“项目已完整防 SSRF”。生产化应先收口为已上传资产 ID/受控对象存储，禁止任意本地路径；远程 URL 需 DNS 解析后校验并防重绑定、限制重定向/大小/超时。

### 安全与工程追问（面试官很可能继续问）

**Q：既然查询都带 `userId`，为什么还不能说多租户隔离完成？**

数据访问确实把 `userId` 带到草稿、修订、RenderRun 查询中；但它来自可伪造的 `x-user-id`，不是已验签身份。当前只能说“仓储接口预留了所有者作用域”，不能说真实鉴权或租户隔离。生产化顺序是先接可信身份（JWT/session）并由网关/中间件写入身份上下文，再做 RBAC、资源所有权校验和审计。

**Q：你们的 SSRF 防护做到什么程度？**

外部图片/发布地址有基础分类：禁止本机名、私网 IP 字面量和非 HTTP(S)。这只能减少 Provider 被喂入明显内网地址的风险，不能覆盖 DNS 重绑定；而样片分析接口仍会由服务端直接下载任意 HTTP URL，且支持本地路径。因此正确答案是“有局部地址校验，但样片读取是待收口的高优先级缺口”，不是“已经解决 SSRF”。

**Q：上传安全怎么回答？**

当前有 200 MB 限制、UUID 落盘、内容 hash 复用和受控 `/uploads/<filename>` 解析，重点是避免名称冲突与路径穿越；没有根据文件魔数校验真实类型，也没有杀毒/沙箱转码、配额、生命周期清理或私有下载。这些必须在面向公网前补齐。

**Q：模型生成的前端/Remotion 代码为什么不直接执行？静态审计够不够？**

不是直接信任：先限制 import 来源，拒绝 `fetch`、`eval`、动态 import、浏览器存储、资源加载标签、随机/计时 API 等，再编译、试渲染并做视觉验收；引用时还验证组件用途和画布证据。但这是静态 allowlist 审计，不是操作系统级隔离。生产化应把构建/渲染放进最小权限容器，限制 CPU/内存/网络/文件系统，并设置超时和资源配额。

**Q：外部视频生成超时，如何避免重复扣费？**

同一渲染 key 的素材 job 会复用持久 receipt，Provider 已返回的 task ID 会被保存；同一渲染请求也有 receipt 回放。缺口在“Provider 已接单但提交响应还未携带 task ID 就中断”：当前没有 Provider 幂等键透传或按客户端 key 查询的恢复协议。面试时应明确说这是下一步要与供应商能力对齐的边界。

**Q：上线后先补哪些工程能力？为什么？**

优先级按风险排：可信认证与资源鉴权、样片读取的 SSRF 收口、上传扫描/私有访问/配额、限流与成本预算、trace 脱敏和保留策略；随后才是异步队列、恢复调度、监控告警和多机扩展。前五项先解决“谁能访问、能读什么、会不会外带或被滥用”，而不是先追求吞吐量。

### 实际工程高频追问地图

以下不是泛泛的八股，而是从当前项目的“模型 + 可编辑工程 + 外部生成 + 本地渲染”组合自然会追问到的题。每一题都先答**当前已实现的边界**，再说**尚未生产化的部分**：

| 面试官可能问什么 | 回答抓手（当前代码事实） | 不能夸大的地方 |
|---|---|---|
| 谁是视频工程的唯一事实？前端改乱了怎么办？ | 后端草稿/Revision/RenderRun；保存走 `baseRevision` 条件更新，冲突返回 409 | 真实身份仍是占位 header，不能称多租户已完成 |
| LLM 输出错 JSON、选错 Tool 怎么办？ | Zod 解析、一次 JSON 修复、Skill-Tool 白名单、参数/依赖/意图/就绪门禁 | 不能报未验证的一次成功率 |
| 一次局部修改如何确保没把其他镜头改掉？ | 服务端 scope 合并、Reviewer、结构/组件/提交门禁 | 语义审查不是数学证明，质量指标要以实跑为准 |
| 同一渲染点击两次、网络重试、并发请求怎么办？ | `Idempotency-Key` receipt、请求 hash、同进程 in-flight 合并、RenderRun 回放 | 预览/保存/组件创作/整轮对话并未全覆盖；崩溃恢复也未完成 |
| Provider 超时或“已接单但没回 task ID”怎么办？ | 已取得 task ID 会写 receipt；fallback 按 material job 声明 | 没有 Provider 幂等键透传/查询协议，未知受理状态仍是缺口 |
| 为什么同步渲染，不上队列？何时改？ | 当前 desktop-first，REST 请求内完成指定修订 | 不适合高并发、重启恢复、可靠取消；需要时用 RenderRun/revision 重建队列 |
| 如何防模型生成恶意组件或非确定性渲染？ | 静态 import/identifier/资源标签审计、编译、试渲染、视觉验收、组件引用校验 | 静态审计不等于容器级隔离，仍要资源限制和 sandbox |
| 用户上传、远程素材和样片 URL 怎么防攻击？ | 上传目录/文件名受控；Provider 图片 URL 做基础地址分类 | 样片分析仍可直接读任意 HTTP/本地路径，是 P0 收口项；无病毒扫描/MIME 嗅探 |
| 如何观测和排查一次失败？ | 运行 trace、工具门禁原因、Revision/RenderRun 状态、素材生成 trace | 未见生产级指标、告警、trace 脱敏和长期保留治理 |
| 如何控制成本与滥用？ | Tool 卡有成本档、讨论轮不执行 Tool、日常确定性回归可关闭真实生成 | 没有可信身份下的限流、配额、预算或计费闭环 |
| 如何评测 Agent，而不是只看最终回复？ | 对工具、范围、版本、门禁做确定性断言；另有回复质量/真实出片分层 | 最新报告是 deterministic-only，不外推为线上质量或审美结论 |

答题顺序建议固定为：**先说明对象和信任边界 → 讲当前门禁/状态流 → 点出失败路径 → 诚实说明还没生产化的缺口**。这样不会因为“只背最佳实践”而被继续追问击穿。

**Q：生成模型断了怎么办？**
生成能力做成可替换接口：配置真实 Provider 时才会调用外部生成；未配置时 Noop 适配器返回失败。素材任务若声明了 fallback，解析器会按声明降级；未声明 fallback 则本次运行失败，不能说“一定会出兜底画面”。评测可以关闭真实生成以控制成本，因此排查时必须区分运行模式、外部依赖与真实出片是否实际执行。

**Q：图片怎么给生成模型？**
识图和图生视频共用同一个服务端素材身份，但末端协议不同：Director/Planner 通过公网 `input_image` 或临时 Ark Files `file_id` 读取像素；Planner 只记录 `input_asset_id`。只有真正执行对应 Seedance 图生视频任务时，服务端才把该图片发布并绑定成公网 URL，已经公网的图片原样透传，避免无关素材在规划阶段阻断任务。

### Agent 专项追问（记忆 / 压缩 / 结构化输出 / 工具编排）

**Q：上下文压缩怎么做，会不会丢关键事实？**
保留最近四轮原文，更早内容滚动压缩成摘要；已确认的创作约束作为独立权威状态注入，长期记忆从独立存储检索，不依赖摘要记住。每轮执行结果也会以事实形式回写会话。压缩正确性有测试；不在未验证的 live 报告中声称事实召回率。

**Q：创作记忆怎么防脏数据？**
三件事：模型推断或不确定的偏好只能作候选、不直接控制创作；用户明确要求保存的稳定偏好才可生效；撤销过的同项偏好再次出现会回到候选；每条记忆记录来源（哪一轮、哪句话），可追溯。相关门禁有确定性用例，live 指标须以实际运行报告为准。

**Q：记忆怎么参与创作？**
Director 路径会按用户/草稿作用域检索记忆，并把 active 结果带入相应上下文；candidate 不作为时间线规划事实。用户级记忆不等于无条件覆盖所有项目：当前输入和当前项目要求优先。检索结果会写入相关 trace，具体命中质量仍应以报告为准。

**Q：结构化输出为什么一次通过率高？**
模型的工具提议和状态动作受结构化 schema 约束；服务端先校验再执行，字段错或范围不对直接拒绝。导演路由的 JSON 解析失败时只做一次格式修复请求，仍失败则安全地回到非执行回复或上下文兜底，不让整轮对话崩掉。当前不报未验证的一次通过率或降级率。

**Q：工具和技能为什么分开注册？**
技能说明“这类任务怎么做”（含具体操作指令），工具是“具体动作”。模型必须先选中技能、再绑定该技能名下的工具，同轮校验；这防止模型绕过业务边界凭空调用动作。选错了服务端会拒绝并给出可用替代项。

**Q：交付授权怎么判断，不怕模型假装用户授权吗？**
当前授权不靠匹配“渲染”两个字，而是由本轮模型结构化结果同时满足“意图为执行、提出正式渲染、用户文本非空”后才放行。它能阻止普通聊天误触发交付，但仍是模型参与判定的原型级控制，不是独立的前端二次确认或生产级授权凭据。生产化应把高成本/外发动作改成服务端签发的、可过期的显式确认令牌。

**Q：模型选错工具或改错范围怎么办？**
执行前会做就绪检查，再校验参数与范围；拒绝时返回结构化原因和恢复建议，结果写回会话供后续轮次参考。失败恢复率需要完整 live 回归或真实运行证据，当前不报此指标。

**Q：如何避免评测只对测试集有效？**
不会只看一套数：确定性检查是程序断言（动作、工具、状态、版本对不对），回复质量应由独立模型裁判或人工抽检；评测分离线、真实模型、真实出片三层，记忆评测另设 hard 场景。若最新报告只跑 deterministic-only，就只报告它实际覆盖的部分，不把它外推成 live 质量。

**Q：时延和成本怎么控制？**
每轮会留下模型调用与工具执行证据；纯讨论轮不触发工具；失败后恢复走非执行回复；日常确定性回归关闭真实生成以控制成本。当前题库不固定填写 p50/p95：只有在拿到同一环境、同一模型、带日期的压测报告时才报时延。

## 6. 踩坑故事（只讲你有证据的一两个）

下面是可选讲法，不是仓库自动证明的个人经历；只有能拿出 issue、trace 或回归记录时才用第一人称。

1. **规则误伤正常表达**：将目标校验写得过严，可能会误拒本来合法的局部字幕修改。教训：输入尽量宽容、状态变更严格；加规则前先补反例。
2. **评测环境 vs 真实环境**：评测脚本可以关闭真实生成以控制成本，真实运行配置可打开生成。教训：排查前先确认测试运行模式、外部依赖和真实出片是否实际执行，不能用一种环境的结论替代另一种。
3. **文本断言与语义不一致**：若只用精确字符串判断跨轮要求，模型换一种说法就可能被误判。项目当前检索是轻量关键词方案，是否需要语义判定或向量检索，应以 hard 集和实际 badcase 决定。

## 10. 工具调用类（Agent 岗高频，几乎必问）

**Q：Agent 为什么要调用工具？**
因为大模型本身有三大短板：信息是训练时的（要查实时数据）、只能输出文字（没法真正操作业务）、回答靠概率（需要确定性校验）。工具就是补这三块：实时性、操作性、确定性。

**Q：Function Calling 和你的方案是什么关系？**
我们不用模型厂商的原生 Function Calling，而是让模型输出一份**结构化的工具请求 JSON**，由后端解析、校验、执行。这样协议与厂商解耦——换模型不改业务协议。原生 Function Calling 未来可以作为“适配层”，但内部仍然翻译成同一份协议。

**Q：模型和后端各自负责什么？**
模型负责“理解和表达意图”：选哪个工具、传什么参数、依赖什么；后端负责“执行与把关”：参数校验、身份/版本绑定、权限、工具级去重、真实执行、结果回写、失败处理。渲染请求已具备同 key 的 receipt 回放；草稿预览/保存、组件创作和整轮对话没有同等覆盖，不能泛称“后端所有写操作都幂等”。一句话：**模型提议，后端决定。**

**Q：当前实际注册了哪些 Tool？**
当前真正对 Director 暴露的是 6 个 `available` Tool，不要把 `planned` 的音频能力说成已可调用：

| Tool | 作用 | 模型可填参数 | 后端绑定/门禁 |
|---|---|---|---|
| `sample.analyze` | 分析已选样例的视频结构、节奏和风格 | 无 | 样例 ID 由当前上下文选定；没有已选样例则 blocked |
| `material.inspect` | 查看当前候选素材 | 无 | 素材集合由服务端当前上下文绑定；无素材则 blocked |
| `timeline.plan` | 创建完整可编辑时间线草稿 | 可选 `instruction` | 已有草稿时禁止再次 plan，必须走 patch |
| `timeline.patch` | 修改已有草稿 | `scope`、目标 scene/transition ID、可选 `instruction` | scope 只允许 subtitle / scene / structure / visual_strategy / transition / global；目标、草稿和修订由服务端校验/绑定 |
| `timeline.render` | 渲染已保存修订 | 无 | 草稿与 revision 由服务端绑定；属于 delivery，必须是 execute 意图且通过当前交付门禁 |
| `render.author` | 创建场景/转场自定义组件 | `purpose`、效果名、效果说明、验收条件 | 服务端编码 Agent 负责生成、静态审计、试渲染和视觉验收；后续方案须显式依赖结果才可引用 |

`audio.plan`、`audio.generate_tts`、`audio.align`、`audio.mix` 在注册表中是 `planned`，不会通过可用 Tool 卡提供给模型。要求台账的 `stateActions` 与创作记忆的 `memoryActions` 也是模型的结构化输出，但它们不是这 6 个 Tool。

**Q：模型在当前系统里如何 Tool Use？**
不是让模型直接调用 JavaScript 函数。Director 先把 Skill 卡、可用 Tool 卡（含输入 JSON Schema、成本档和权限要求）以及压缩后的权威上下文放进提示词；模型只输出结构化 JSON：`intent`、`toolRequests`、`skillRequests`、`stateActions`、`memoryActions` 等。

每个 `toolRequest` 要带 Tool、主 Skill、参数、局部 `ref`、`dependsOn` 和请求模式。模型输出先过 Zod 协议解析；格式/字段失败时只发起一次“只修 JSON 格式”的修复请求，仍失败就退回不执行的安全回复或上下文兜底。解析成功后，后端再依次做：Skill 是否存在且允许该 Tool → 参数 schema → 依赖是否只指向已完成的前序动作 → chat/clarify 是否禁止执行 → delivery 是否要求 execute → 工具就绪条件与授权 → 服务端绑定 user、素材、草稿、revision、目标 ID → Dispatcher 真正执行。Tool 结果、门禁原因和草稿版本再写回权威会话并通过 SSE 事件返回前端。

**Q：工具调用上线后有哪些工程风险？你们怎么防？**
- 参数幻觉 → 严格 schema 校验，系统字段后端绑定，模型传了直接拒；
- 越权/误操作 → 动作分只读/改草稿/交付三档；当前交付有本轮意图门禁，生产化再补不可伪造的显式确认令牌；
- 重复调用 → Director 工具调用有调用号去重；编辑器直连渲染已使用 `Idempotency-Key`、持久 receipt 和同进程 in-flight 合并。草稿预览/保存、组件创作和整轮 Director 对话仍需补同等的结果回放；
- 工具失败 → 返回结构化失败与恢复建议；失败的渲染运行会标记失败，不会写成成功产物。是否保存新的草稿修订取决于具体工具路径，不能笼统说所有失败都不写状态；
- 成本放大 → 工具卡精简、一次能做完不让模型绕路、失败不盲目重试。

**Q：工具很多时模型怎么选？**
给模型的是当前可用的 Skill/Tool 卡片，而不是让它猜能力：Tool 卡含名称、作用、成本档、输入 schema、可绑定 Skill 和是否需要授权；Skill 卡负责“这类任务怎么做”。模型先选 Tool 的主 Skill，再提出 Tool 请求；后端只为实际被选中的 Tool 加载该主 Skill 的完整内容及其受控依赖参考。避免把所有技能正文都塞进每一轮上下文。

**Q：工具返回失败后怎么处理？**
统一转成结构化失败：发生了什么、为什么、怎么恢复；同时把失败原因写进证据链（并标注是哪个环节拒的），下一轮可以继续而不是卡死。

## 11. 评测类（“Agent 怎么评测”是高频大题，参考业界八维框架）

**Q：Agent 评测和普通模型评测有什么区别？**
普通问答看“答案对不对”；Agent 是多步执行系统，要同时看结果、过程、工具、成本、稳定性、安全。只看最后一句答没答对，会漏掉“过程很糟但结果碰巧对”的大量问题。

**Q：你从哪些维度评？**（用八维框架 + 我们的做法）

| 维度 | 我们怎么做 | 数据/证据 |
|---|---|---|
| 任务完成率 | 对每轮断言“该建的方案建没建、该改的改没改” | 以带日期/提交的回归报告为准；最新 deterministic-only 不产出 live 完成率 |
| 结果质量 | 独立裁判模型评自然回复，另有人工抽检计划 | 最新 deterministic-only 未运行裁判，不能填写通过率 |
| 过程质量 | 断言“该用工具时用了、不该用没用、没改不能假装改” | 有专项断言（工具选择、范围、零差异） |
| 工具调用质量 | 校验工具选得对不对、参数合不合法、结果成不成功 | 有专项确定性断言；live 准确率须以实跑报告为准 |
| 检索质量 | 偏好记忆召回按 easy/hard 两套集测 | 最新快照：easy Recall@8=100%，hard=75% |
| 性能与成本 | 记录单轮耗时与 token | 当前未维护可对外背诵的统一压测数字 |
| 稳定性 | 失败恢复轮、工具失败降级轮 | 有专项轮次，不注入失败时不误判 |
| 安全与权限 | 覆盖未授权执行、越权改草稿、系统字段覆盖 | 有确定性用例；最新 deterministic-only 不可外推为 live 的 0 风险 |

**Q：离线评测和在线评测？**
离线：冒烟集（核心链路能不能跑通）、回归集（历史问题不复发）、行为评测集（该不该调用工具、失败后怎么降级）、安全评测集（越权/敏感操作）。仓库具备这些方向的离线脚本与数据。在线：真实上线后看任务完成率、错误率、延迟、成本、用户反馈——**当前没有匿名真实线上流量证据**；trace 与事件流可帮助定位，但不能替代线上指标。

**Q：LLM 当裁判可靠吗？**
不可全信。原则是：**规则能判的用规则，结果能验证的用结果，只有主观评价才用裁判模型 + 人工抽检**。我们就是这样：意图/工具/范围/版本用确定性断言，回复质量才交给裁判，且关键轮次有人工抽检计划。

**Q：失败样本怎么回流？**
建议把失败样本记录根因、修复与验证，并沉淀进回归集。仓库已有回归台账和专项 smoke，但不能声称代码会自动把每次失败登记、或强制每条新规则都附反例。

## 12. 记忆与上下文工程类

**Q：LLM 无状态，怎么让它记住多轮对话？**
分层：最近原文、滚动摘要、结构化“当前项目要求”台账、当前草稿事实和跨项目长期偏好。前端刷新不丢：工作区会话由服务端文件仓储持久化，恢复时带回草稿、版本、要求等权威状态。

当前压缩是**确定性裁剪，不是 LLM 自动摘要**：一次标准对话会追加一条 user 记录和一条 assistant 记录；会话超过 4 条记录时，只保留最新 4 条原文记录（通常约两轮问答）。更早记录逐条压成 `role: 内容 [intent] => outcome`，每条内容先去空白并截到 600 字符，再与已有滚动摘要拼接，只保留末尾 4,000 字符。这个摘要和最近原文只用于理解指代、延续与冲突，不拥有状态写权。

不会依赖这段摘要记住关键事实：当前草稿/修订、时间线事实、有效要求、UI 明确控制、素材摘要、最近失败和执行结果都由服务端作为独立结构化字段注入；创作记忆按本轮输入检索，active 与 candidate 分开注入。当前用户输入优先于有效要求，历史摘要优先级更低。

**Q：短期记忆和长期记忆怎么区分？**
短期=本会话的工作区状态（草稿、版本、最近结果）；中期=本项目的“要求台账”（这单的合同）；长期=跨项目的创作偏好（以后都这样）。三者写入时机、有效期、用户可见性都不同。

**Q：记忆会不会过期或冲突？**
会，所以有机制：要求可以被显式替换/撤销；偏好有“待确认候选”状态，模型猜的不能直接生效；被撤销过的偏好不会被悄悄复活；当前输入永远压过历史记忆。

**Q：为什么没用 RAG？**
当前需要召回的是用户偏好而不是文档知识，实现采用关键词/BM25 式召回；最新 hard 集快照的 Recall@8 是 75%，因此向量检索是明确后续项。代码和该快照没有提供“语料小到无需向量检索”的容量阈值，不要把“体量小、当前方案够用”说成量化结论。

**Q：什么是上下文工程？你们做了什么？**
让模型在有限上下文里看到“该看的、最新的事实”：当前实现把会话压缩后的 `conversationMemory`、当前 prompt、运行时能力快照、Tool/Skill 卡、草稿与 timeline facts、有效要求、近期要求变动、样例/素材摘要、检索到的 active/candidate 记忆、已提升组件和当前图片输入分别注入。它不是“把所有历史聊天塞进去”，也不把旧摘要当权威；系统字段由服务端重建并绑定。当前压缩上限按记录数和字符数控制，没有已验证的 token 预算或线上时延指标，面试中不要补成具体 token 数。

## 13. 系统设计与扩展类（可能被要求“现场设计”）

**Q：怎么新增一个能力（比如加一种修订范围）？**
讲出我们的扩展点流程：定协议（输入 schema）→ 定义“允许改什么”的范围表 → 接入统一的门禁（没改不能假装改）→ 加目标绑定与校验 → 加反向用例测试 → 登记规则台账。面试官会认可“有一套固定扩展流程”而不是临时改。

**Q：怎么保证正确性和一致性？**
四个词：**唯一权威**（执行都在服务端）、**不可变**（修订只增不改）、**版本保护**（改的时候必须基于最新版，冲突就报错）、**门禁**（没改不能假装改、越权字段一律丢弃）。

**Q：怎么控成本与延迟？**
当前靠工具卡精简、上下文裁剪、确定性兜底、关闭日常评测中的真实生成，以及可配置的素材生成并发控制成本。工具注册表有成本等级，但没有真正按成本自动切换不同模型；模型级路由是后续能力，不能说已经实现。

**Q：怎么扩展多用户/生产化？**
草稿、修订和记忆查询都带 userId 作用域；但当前身份来源仍是本地占位头，不能把它说成完成了真实多租户隔离。本地使用文件库，关系型数据库路径由 Prisma 提供；当前形态偏单机/本地，真实部署、鉴权、监控和配额仍是后续项。

**Q：ReAct 和你的方案什么关系？**
我们的模式可以看作 ReAct 的工程化变体：模型“想（规划）→ 提议工具”，但“执行与验证”在服务端完成，并且每一步都有审查门禁和证据记录；比起纯 ReAct 的“模型反复自循环”，我们把确定性控制从模型手里拿回到系统手里。

**Q：生产落地最大的难点是什么？**
模型行为的不稳定与系统规则之间的平衡：规则太严误伤正常表达，太松又不可控；所以核心是“输入宽容、状态严格、语义交给模型”，并靠失败登记制度持续校准。

## 15. Agent 基础与框架选型（八股速答）

**Q：什么是 AI Agent？核心组件是什么？**
Agent 是“能自己决定下一步做什么”的程序：理解目标 → 拆解步骤 → 调用工具 → 看结果 → 调整。核心组件是规划（拆任务）、记忆（记住上下文和偏好）、工具（操作外部世界）、行动（执行并反馈）。普通问答模型只做最后一环，Agent 把四件事串成一个循环。

**Q：ReAct / Plan-and-Execute / Reflexion 各是什么？你们属于哪种？**
- ReAct：每步“想一下 → 做一下 → 看一眼结果”再继续，适合边做边调整的任务；
- Plan-and-Execute：先一次性定计划再逐步执行，适合计划相对稳定的任务；
- Reflexion：做错了先自我复盘，把教训写进记忆再重试。

我们更接近 Plan-and-Execute 的工程化变体：每轮先理解意图、确定要动的范围，再执行；执行中有校验和记录，不依赖模型无限自循环。它适合“需要受范围约束的方案修改”这一类场景；是否符合真实用户偏好仍需用户研究或线上数据验证。

**Q：为什么不用 LangChain/LangGraph，为什么自研？**
当前仓库没有引入 LangChain/LangGraph，而核心代码确实集中在草稿/修订/渲染版本、范围修改和记忆作用域等业务状态上。面试时可解释为“这些业务规则仍需要自己建模，框架不能替代”；但代码无法证明当初没有采用框架的唯一原因，也不能断言“框架给不了”或“当时的决策一定最优”。更准确的表述是：若重做，应评估状态图框架是否能降低编排样板代码，同时保留当前协议和门禁。

**Q：单 Agent 还是多 Agent？为什么？**
不要回答成固定的“两 Agent”。当前更准确的表述是：**一个 Director 编排 Agent，加按场景启用的受控专业模型模块**，它们不是平权自治协商。

- **Director Agent**：持有用户会话、创作要求和当前草稿上下文，负责理解意图、选择 Skill/Tool、提出执行动作；它不直接绕过后端写草稿。
- **LLM Planner**：在 `timeline.plan` / `timeline.patch` 中生成候选 `RemotionTimelineSpecV1`；没有独立会话、工具权限或草稿写权。
- **Timeline Outcome Reviewer**：读取用户要求、基线/候选事实摘要、diff 与 scope，返回 `pass / violations / repairInstruction`；不改方案、不落库。Planner 失败后最多带审查意见修正一次再审。
- **Component Authoring Agent（可选）**：仅当预置效果与已注册组件不足时由 `render.author` 调用；它生成组件并完成静态审计、试渲染和视觉验收，返回组件 ID。后续时间线请求必须显式依赖这个工具结果，组件 Agent 也不能直接修改草稿或交付视频。

所以，普通规划链路有 Director、Planner、Reviewer 三个模型角色；需要新特效时增加组件创作 Agent，成为四个顶层角色。若把组件内部的视觉验收模型调用也逐一算 Agent，数量会继续变化，故不要在没有先说明统计口径时只报一个数字。更稳妥的结论是：**写权限集中在服务端，模型角色按受控工作流协作。**

**Q：MCP 是什么？和你的技能/工具体系什么关系？**
MCP 是让 Agent 连接外部工具/数据源的标准化协议：服务端统一暴露资源、工具、提示词。我们的技能/工具注册表本质上是同一思路的轻量实现：工具 = 具体动作（登记参数 schema），技能 = 一类任务怎么做（含操作指令），模型必须先选技能再绑工具。接外部服务时用 MCP 标准暴露更省事；但内部核心工具仍走自己的协议，因为要带版本、范围、门禁这些业务语义。

**Q：原生 Function Calling 的原理是什么？为什么你们不用？**
原生 Function Calling 是模型厂商内置能力：你在请求里声明一批函数（名称 + JSON Schema），模型输出“调用哪个、传什么参数”的结构化结果，由你的代码执行。本质是把工具清单写进上下文 + 让模型按格式输出。当前实现让模型输出并解析自己的结构化工具请求，再由服务端做业务校验；无论是否使用厂商 Function Calling，目标、版本和范围都仍需服务端强校验。代码没有记录当初拒绝原生 Function Calling 的唯一原因；若接入，可在适配层翻译到同一份内部协议。

**Q：LLM 基础速答：幻觉、temperature、JSON 输出、上下文窗口、模型选型？**
- 幻觉：模型生成训练数据里没有或与事实不符的内容，本质是概率生成没有“事实核查”。缓解：工具返回的事实直接注入、结构化校验、精确数字从工具结果提取而不是让模型背。
- temperature：控制随机性，越低越确定。工具调用相关输出用低温度，创意文案用中高。
- JSON 输出：用 schema 约束格式，但服务端永远再校验一次，不信任模型输出。
- 上下文窗口：模型能同时看到的最大 token 数，超了会截断或报错，所以要精选注入 + 压缩。
- 模型选型：当前由配置指定 Director、视频理解和视频生成模型，工具卡只有成本标签，**尚未实现**按任务难度自动切不同 LLM。生产设计可以按意图、风险、时延和质量分档，但不能说已落地。

## 16. Loop Engineering 与 Badcase 闭环

**Q：什么是 Loop Engineering？你们怎么做的？**
把 Agent 的“循环”从 while(true) 变成可控工程：循环条件、步数限制、状态更新、异常处理、观察裁剪。我们单轮循环内：模型决策 → 后端校验 → 执行 → 结果回写；每轮有明确结束标志（用户收到回复、状态同步）；失败不盲目重试（一次格式修复请求，再失败走确定性降级）；工具返回内容精简成事实回写，不把几百行明细塞回上下文。

**Q：Checkpoint / 状态回退 / trace 回放怎么做的？**
- Checkpoint：草稿的每个修订版本都是不可变快照（改前快照 + 改后快照），任何时候能回答“第几版改了啥”；
- 状态回退：失败时草稿不落新版本，工作区保持上一稳定版，下一轮模型可以修正重试；
- Trace 回放：每轮对话、每次工具调用、每个拒绝点（带环节标记）都写证据，出问题按时间线回放“模型怎么走到这一步的”。

**Q：出现 Badcase 怎么快速定位环节？**
三步：先看 trace 时间线（哪一轮、选了哪个工具、参数是什么）；再看拒绝点标记（参数校验拒的、范围校验拒的、版本冲突拒的、没授权拒的——每处都写清环节）；最后归因：是模型理解错、规则误伤、还是上下文没带够。归因后进失败台账，标“根因、修复方式、验证方式”。

**Q：Prompt 调优“修好一类、坏了另一类”怎么解决？**
这是规则/提示词的回归问题。开发流程文档要求新规则带反例测试，并将问题按硬约束、输入宽容和语义判断分类；实际是否全量执行需看对应运行记录。若要讲“改视觉呈现误伤字幕修改”的具体故事，必须确认你有该问题的 trace、修复和回归证据；否则只讲通用方法：先加反例，再调整服务端目标绑定或输入校验，最后用回归验证。

**Q：Badcase 回流到 SFT 的链路？你们有吗？**
当前仓库没有 SFT 训练或模型权重更新链路。已有的替代做法是把失败归因到模型理解、规则、上下文或数据集，再通过提示词、规则、数据集或协议修复并回归；执行是否完整仍需看台账与运行记录。如果被问何时考虑 SFT，可回答：当同一类错误跨场景稳定出现、且规则层已收敛时，才评估训练数据和模型微调。

## 17. 幻觉、检索与 RAG 通用题

**Q：高准确性场景怎么控制幻觉？**
原则：事实必须来自工具结果，不让模型背。四招：结构化约束（schema 限制格式）；事实注入（版本号、镜头列表、有效要求都是服务端给的，不是模型记的）；后置校验（模型声称“已修改”但内容没变 → 拒绝；镜头编号不存在 → 友好拒绝并列出可用项）；精确数据从工具返回提取。

**Q：幻觉率、引用错误率多少？业务上能否接受？**
诚实回答：没有按“幻觉率”口径统计过，因为我们不是问答型 RAG——更应盯“模型编造镜头编号/版本号/声称改过”这类操作幻觉，靠后端绑定与门禁兜底。如果面试官要指标，可以现场定义：操作幻觉 = 模型提出工具请求但目标不存在、参数非法或与授权范围不符；现有确定性用例覆盖这些门禁，但最新 deterministic-only 报告不能证明 live 风险为 0。

**Q：查询改写、rerank、混合检索？**
标准 RAG pipeline：Query 改写（消指代、扩同义）→ 多路召回（关键词 + 向量）→ 融合（如 RRF）→ 重排（rerank 精排）。我们项目里的简化版是偏好记忆的关键词/BM25 式召回，加连续中文短语匹配兜底；为什么没上向量检索？语料是用户偏好不是文档，体量小，当前方案够用。hard 集 Recall@8=75% 是该评测快照下“下一步上向量检索”的依据，而不是线上承诺。

**Q：多轮对话上下文断裂怎么办？**
两层：写入侧，每轮把“当前有效要求台账、已确认记忆、最新版本快照”注入，不依赖模型自己记得；读取侧，保留最近几轮原文、更早内容滚动摘要，但已确认的约束不进压缩范围。事实回写让模型每轮看到的是服务端权威状态，而不是从长对话里翻。

## 18. 成本、性能与生产化

**Q：准确率和效率怎么平衡？**
当前已落地的是上下文预算（只注入权威状态和精简工具卡）、避免无效工具调用、失败降级，以及工具成本标签；没有按简单/复杂任务自动切换不同模型的模型级路由。生产化可在有真实成本和质量数据后按意图、风险与时延做分档路由，不能把这项方案倒写成现状。

**Q：LLM 推理优化（vLLM、KV Cache、continuous batching）？**
诚实讲：我们是应用层，没做模型服务层优化。原理可以讲：KV Cache 缓存已算过的注意力键值避免重复计算；continuous batching 让不同请求动态拼批减少等待；量化降内存。面试这样答：先说明自己负责的应用层优化（成本档、上下文预算、失败不盲试），再说这些属于推理服务层，生产化要接的话是部署团队的事，不是应用代码。

**Q：超时、重试、熔断怎么设计？**

先区分四件事：**超时**是停止等待；**重试**是再发一次相同操作；**轮询**是等待一个已知外部任务结束；**兜底**是换一种可接受的结果。当前代码按环节处理，并不是“一个统一重试器”：

| 环节 | 当前超时/重试 | 失败后的行为 | 不能夸大的地方 |
|---|---|---|---|
| Director 意图路由 | 模型请求受 `DIRECTOR_AGENT_TIMEOUT_MS` 限制（默认 120 秒）；若 Provider 不支持 JSON Schema 且返回 400/404/422，会只重发一次不带 schema 的请求 | JSON 解析失败只请求一次格式修复；再失败返回安全的非执行回复或上下文兜底，不猜测并执行 Tool | 网络/超时不会自动重试；整轮 Director 请求也没有 receipt 回放 |
| 时间线 Planner / Reviewer | 调用模型也使用 Director 超时；结构化输出不被支持时可去 schema 重发一次，JSON/字段错误各有一次修复路径 | **已有草稿的修订**若 Planner/Reviewer 仍失败会拒绝保存，绝不拿无关联的确定性方案覆盖旧版；初始规划在允许且输入条件安全时才退到确定性方案，否则生成带 planning gap 的方案说明问题 | 这不是保证 LLM 一定可用，也不是无限自我修复 |
| 样片理解 | Files 上传、模型请求用 `VIDEO_UNDERSTANDING_TIMEOUT_MS`（默认 300 秒）；预处理状态轮询有 `VIDEO_UNDERSTANDING_FILE_READY_TIMEOUT_MS`（默认 180 秒）与轮询间隔 | 模型、文件预处理、JSON 解析失败时回到本地抽帧/音频/元数据生成的启发式理解，并记录 warning；临时云文件在 finally 中尽力删除 | 远程样片下载本身没有看到 `AbortSignal`、大小上限或重定向限制；不能说样片链路端到端有严格 deadline |
| Director/Planner 图片输入 | Ark Files 上传/查询使用 Director 超时，文件状态轮询有独立 ready timeout | 单张图片失败只记 warning、忽略该输入，其他图片和文本规划仍可继续；临时文件删除失败只告警 | 这会降低视觉条件质量，不保证“素材失败后仍满足原图要求” |
| 外部视频生成 | Provider 提交单次最多 60 秒；总轮询窗口默认 180 秒、间隔默认 3 秒；下载单次最多 120 秒 | 已拿到 task ID 会写入 receipt；普通生成失败按 material job 的 `fallback_asset_id` 或 `blank_card` 处理，没有 fallback 则整个渲染失败 | 轮询不是重新提交；没有指数退避/熔断，也没有 Provider 幂等键透传。提交已发出但 task ID 未返回时标为 `unknown`，**禁止**静默 fallback，避免把可能已扣费的任务伪装成已恢复 |
| 素材解析与标准化 | 可配置并发默认 3；同一 render key/material job 可复用 receipt 或上一成功 Run 的同指纹素材 | 常规生成失败可复用备用素材或保留显式 blank-card 场景；交付前检查素材完整性，不满足就失败，不出“假成功”的 MP4 | 备用策略由每个 job 声明，不是所有镜头天然都有 fallback |
| 自定义组件创作 | 代码模型调用走 Director 超时；最多 3 次编码尝试，代码问题与视觉验收问题各只允许一次修复方向 | 静态审计、编译、试渲染或视觉验收失败时删除 draft 组件；视觉审查协议失败直接返回失败 | 没有跨请求组件创作幂等和队列化恢复；静态审计不是资源级 sandbox |
| Remotion 渲染与清理 | 子进程失败会 reject；临时目录删除最多重试 10 次、间隔 100 ms | Run 标记 failed，清理本次输出目录，相关组件可标记 render failed，receipt 记为 failed | `spawn` 没有看到渲染总超时、取消信号或资源上限；卡住的子进程仍是当前同步架构的缺口 |
| 编辑器侧 | 首次 POST 网络异常只用**同一个** `Idempotency-Key` 重试一次；收到 202 后每秒查询同一 RenderRun | 已完成时再用同 key POST 取回同一结果；失败抛出错误给 UI | 前端轮询没有总时限或取消控制，长期 `running` 需要服务端恢复器/用户可见的超时策略 |

可以这样总结给面试官：**“我们优先把不可安全重试的外部提交识别成 unknown/失败；能保留用户体验的地方才按协议显式降级；能安全重放的渲染请求靠幂等 receipt。当前没有全局重试、熔断、取消与跨进程恢复，因此同步桌面路径的边界是明确的。”**

生产化应补四件事：为每个外部调用设端到端 deadline 与取消传播；将可安全重试的阶段绑定同一幂等键并做有限指数退避；以 Provider task ID/提交 key 恢复未知状态；用队列 lease、dead-letter、熔断和告警处理长期 running，而不是继续在 HTTP 请求里等待。

**Q：高并发下怎么设计？**
诚实边界：当前 V2 是单机/本地活动路径，渲染仍在请求内同步执行。仓库还保留 Redis 的 Docker compose 配置，但当前 V2 没有接入 BullMQ Worker。生产化可把长任务拆成“素材理解/生成/标准化/Remotion 渲染”队列任务：Job 引用不可变的草稿版本或 RenderRun；数据库事务通过 Outbox 保证状态与入队一致；Worker 用租约、幂等键、有限重试、死信队列处理宕机与重复消费；进度从任务状态推到 SSE 或 WebSocket。以上是生产化设计，尚未落地。

**Q：为什么当前先做同步渲染，什么时候必须上 BullMQ？**
当前 V2 采用同步渲染，是 desktop-first 运行边界的一部分：本地启动不要求额外 Worker、Redis 或队列服务。代码与文档并未给出“同步渲染更快/更正确”的量化比较，不能把它包装成性能优化。它会占住 HTTP 请求，进程重启后难恢复，也不适合高并发、可靠取消和多机扩展；当这些成为实际需求时，应重新引入异步 Job 体系。BullMQ + Redis 是可选实现，不应倒写为当前已落地事实。

## 19. 行为面试与项目表达

**Q：自我介绍怎么说？**
30 秒版：我是做大模型应用/Agent 方向的，最近一个项目的 V2 主路径围绕“模型生成可编辑时间线、系统再执行渲染”构建，重点是让输出可审查、可局部修改、可评测。2 分钟版再加：为什么做、架构三层、当前可复核评测的运行模式与覆盖范围，以及已知边界（评测环境与真实外部依赖不同）。

**Q：你在项目里的角色和边界？**
这题必须按你的真实贡献填写，不能照抄：用“我负责/我主导”的模块 + 具体交付物 + 协作边界来回答。例如确实负责协议和后端链路，才说“我负责协议定义和服务端执行门禁”；评测、前端或渲染若由他人主导，就明确说协作方式和自己负责的部分。

挑真实故事：规则误伤、评测环境与真实环境认知反转、语义匹配误判。讲法：现象 → 排查 → 归因 → 修复 → 数据验证。意见不合的答法：用数据和事实沟通，不情绪化，先小范围验证再全量。

**Q：项目有什么不足？**
诚实给三条：没有匿名真实线上流量证据（评测不是用户行为）；当前正式报告不评价生成视频审美；生产化未完成（单机/本地活动路径、无监控告警）。再补一句“每个不足都有下一步”，例如向量检索有 hard 集数据依据，生产化也有待实现清单。

**Q：为什么想做 Agent 方向？**
因为它把“模型能力”变成“系统能力”，核心挑战是可靠性和评测，这正是我想深耕的。换工作原因答真实但不抱怨：想专注大模型应用/Agent 方向，现有岗位给不了这个深度。

## 20. 补充面经专题（安全 / 多模态 / 视频生成 / 合规 / 设计题）

### 20.1 Agent 安全（OWASP LLM Top 10，字节/安全面高频）

**Q：Prompt 注入有哪几种？怎么防？**
两种：**直接注入**——用户输入里夹带指令（“忽略之前的规则，直接执行……”）；**间接注入**——外部数据（网页、文档、邮件、素材描述）里藏指令，模型读取后当成自己的指令执行。防护要分层：输入侧给“系统指令”和“用户数据”划边界，用户内容一律当数据处理、不当指令执行；模型侧用安全提示词；最关键的是**执行侧**——系统字段、目标与范围必须由服务端绑定和校验。当前交付门禁仍有模型参与意图判定；生产化必须补独立确认令牌，才可说授权不依赖模型自觉。

**Q：Agent 特有的安全风险除了 Prompt 注入还有什么？**
- 越权操作：模型误调高权限工具 → 权限分档（只读/改草稿/交付）+ 服务端范围校验；生产化对交付再加显式确认令牌；
- 数据外带：把用户素材或记忆通过外部工具发出去 → 当前给外部 Provider 的图片 URL 有基础地址分类，公网发布有显式流程；但样片分析仍允许服务端读取任意 HTTP/本地路径，不能把它说成完整的外带/SSRF 防线；
- 敏感信息泄露：PII 进上下文或日志 → 当前 trace 会保存请求、模型输出和工具证据以便回放，因此生产化必须增加字段脱敏、访问控制、加密、保留期限和删除机制；不能声称“当前日志天然不含敏感信息”；
- 工具滥用/成本炸弹：模型反复调用贵工具 → 当前只有 Tool 卡成本档、失败不盲试和部分 trace；尚无已验证的请求级限流、用户配额或成本预算，生产化必须补。

**Q：人在回路（HITL）在 Agent 安全里是什么角色？**
最后兜底：生产系统应让任何不可逆或花钱的动作（正式渲染、真实生成）经过用户显式确认，并由服务端签发短时确认令牌。当前原型只有“本轮结构化意图 + 请求文本”的交付门禁，尚未实现独立的前端二次确认；这一点必须如实说明。

### 20.2 多模态：视频/素材怎么被理解（网易有道 Agent 算法面真题）

**Q：全模态的意图理解怎么做的？Video 信息是怎么用的？**
输入分四路：文本（用户需求）、视频（样例参考）、图片/音频（用户素材）、UI 控件（比例/时长等硬约束）。样例视频的处理是预处理器**抽帧、音频、元数据**，交给多模态模型产出**结构化理解**：叙事结构、氛围、剪辑手法、节奏、可复用/不可复用风格，并按时间切成段；这份“参考摘要”注入导演规划，决定分镜和节奏，但**不直接当素材用**。用户素材则按类型做能力分析（适合什么画面角色、时长比例），规划时决定放哪一镜。关键原则：理解结果必须落到可执行的结构（时间线、素材槽），不是一段漂亮描述；模型不可用时走启发式兜底，不假装理解。

**Q：为什么样例只能当“参考”而不是直接复刻？**
样例视频是风格和结构参考，不是可复用素材：直接复用会带来版权和内容重复问题；而且用户要的是“这个味道”的新片，不是逐帧搬运。所以理解层输出的是**结构化创作事实**（节奏、风格、分镜意图），素材槽由生成模型或用户素材填充。

### 20.3 视频生成基础速答（可灵/视频生成岗位一面）

**Q：视频生成和图像生成的本质区别？**
图像是 2D 静态分布；视频多了时间维度，要同时解决**帧间一致性、运动合理性、长程时序依赖**。所以视频生成的核心难点不是“单帧画得好”，而是“连续几十上百帧又一致又自然”——这也是视频模型普遍比图像模型重、慢、贵的原因。

**Q：为什么主流视频生成用 Diffusion 而不是 GAN？**
Diffusion 训练稳定、覆盖模式广、不易模式坍塌，配合 DiT（Transformer 主干）能较好建模时空关系；GAN 生成快但训练不稳定、多样性差。现在也有自回归与 DiT 混合的路线。面试答“稳定性和可控性优先”即可，不必展开公式。

**Q：你们项目怎么用视频生成？**
视频生成适配器负责“真实画面补全”这一执行环节：当时间线包含 `generate_video` 素材任务、Provider 已配置且任务实际执行时，系统提交生成、轮询状态、下载并标准化后接入时间线。任务是否降级为静态图动效或卡片，取决于该任务的 fallback；否则会失败。它不负责 Director 的意图决策，因此可替换为不同 Provider。

### 20.4 AIGC 内容合规与审核（火山/字节内容安全方向）

**Q：AIGC 生成内容怎么保证合规？**
标准答法是“机审 + 人审 + 模型优化”闭环：接入侧红线词与涉政/涉黄/涉暴检测，生成侧加水印和来源标记，出片前内容审核门禁，投诉和误判回流到规则/模型优化。诚实讲：本项目是原型，当前没有接入商业审核服务，也没有已运行的审核适配器；生产化应在“规划完成后、外部生成前、成片交付前”设置可替换的审核门禁，并把审核结论写入版本和 trace，不能说成“接个配置就已完成”。

### 20.5 现场设计题答题框架（阿里 Offer 面经）

**Q：现场让你设计一个 XX Agent，怎么答？**
框架：**需求澄清 → 边界与假设 → 整体架构 → 数据流 → 关键机制 → 异常与成本 → 评测与上线**。反例是上来堆“RAG + Agent + 多模态 + MCP”名词，却没讲清数据流、异常、成本。正例：先问“用户是谁、输入输出是什么、单用户还是高并发、允许失败吗”；再给分层架构；然后讲一条请求怎么走；最后主动说“哪里会挂、怎么降级、怎么评测、上线先看什么指标”。用本项目当模板演练一遍：意图路由 → 状态/记忆 → 工具编排 → 执行门禁 → 结果回写 → 评测闭环，正好覆盖这套框架每一步。
