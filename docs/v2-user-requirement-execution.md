# AI Video Studio V2：面向真实创作场景的功能审查与优化清单

> 更新日期：2026-08-14
>
> 目的：借助当下 AI 视频工具已形成的用户操作习惯，审查本产品从输入到成片的真实使用场景；定位造成用户困惑、错改、假完成或中断的前后端代码链路，并给出功能优化与可量化的验证方式。
>
> 非目标：不讨论卖给谁、商业化、竞争胜负、售后或组织级运营。本文件只服务于产品功能优化与产品重点提炼。

## 0. 2026-08-14 P0 实施状态

本轮已落地并通过确定性回归：

- F-01：首次创建在执行 <code>timeline.plan</code> 前显示创作摘要，包含目标、受众、画幅、时长、风格强度、必须保留项和待确认信息；摘要与 Planner 输入上下文一并持久化，确认时不重新调用 Director 路由模型，拒绝时不执行规划 Tool。
- F-02：上传在首个网络等待前登记为“上传中”，失败可重试/移除；队列未清空前禁止发送，避免首轮漏素材。
- F-06：属性面板明确为“镜头备注（不会自动执行）”，通过“将备注带入对话”进入真实 revision 流。
- F-05：`timeline.patch` 先形成服务端校验并持久化的修改提案，展示权威 spec 派生的可读目标、时间范围、修改范围和保护边界；确认轮复用同一 canonical callId、原始请求与冻结执行上下文，不重新调用 Director 路由模型。用户取消时不改草稿，服务端确认取消后卡片不再可执行；执行后返回基于持久化前后 spec 的实际 diff。Intent 与终态 Receipt 分开保存和显示。当前纠正方式是带回对话重新提案，不是卡片内直接改写字段。
- F-04/F-07/F-11：镜头按真实产物来源展示用户素材、已生成、待生成、待复用、库存/本地/兜底、失败/缺素材或程序化画面；标题栏只向用户展示“未保存修改 / 当前方案已保存 / 当前方案已生成成片”，不暴露内部 revision 编号；UI、Agent 与正式 RenderRun 共用同一 readiness 判定。确认导出仍在内部精确绑定 draftId+revision，正式 runner 与 RenderRun 创建 seam 都拒绝过期 revision，版本变化后必须重新预飞。
- F-09：RenderRun 可在历史工作台继续查询和取消；本地合成进程可中止，生成服务只有明确处于排队且服务端确认后才显示“已取消”。若提交中、已开始运行、状态不明或只取消了部分外部任务，当前 Run 会失败关闭且不交付，不能虚假显示“已取消”；外部任务仍可能继续，由后续 Provider 能力或 Worker 负责收敛。
- F-12：方案只列出 Planner 实际采用、且能对应到本轮召回事实的历史偏好；“检索到”不再等同于“已经采用”。
- 对话结果：执行事实先汇总为权威回执，再由对话模型整理成自然回复；回复必须逐项回报真实状态，校验失败时回退到保守事实文本。普通用户界面不展示内部版本号和实现术语。

P1 当前进展：冲突时会恢复本轮文字、附件和样例选择；修改回执提供固定问题类型并把澄清要求带回对话；输入附件区明确区分样例参考与成片素材；创作偏好显示来源及已启用、待观察、已停用状态，方案会另列本轮实际采用项；RenderRun 状态可查询，排队中的生成任务与本地合成支持可验证取消。尚未完成：跨设备共享的不满意统计、已运行的远端生成任务取消和独立后台 Worker 恢复。

## 1. 判定标准

| 标记 | 含义 |
| --- | --- |
| **[已验证代码]** | 已直接读取当前源码或现有测试，描述实现事实。 |
| **[市场使用预期]** | 由当前主流产品公开功能反映出的用户操作预期，不是竞争结论。 |
| **[风险推断]** | 从代码路径推导出的可能用户问题；必须经真实任务或 E2E 测试确认频率。 |
| **[待实测]** | 静态代码不足以证明，需记录实际结果。 |

“未发现”仅表示本次阅读范围未发现对应路径，不代表绝对不存在。指标中的数值均为首轮建议门槛，不是假定已经达标的成绩。

## 2. 市场调研只回答一件事：用户现在期待怎样操作

市场资料在这里不用于比较谁更强，而用于避免设计出违背已形成习惯的操作流。

| 已形成的使用预期 | 公开市场证据 | 对本产品的功能要求 |
| --- | --- | --- |
| 用户先给想法/素材，再看可编辑的方案；不是一次生成后只能重来。 | CapCut 将“输入想法 → 选择/调整脚本 → 生成视频”作为基本流，并提供字幕、自动重构图等编辑能力。[CapCut Desktop](https://www.capcut.com/tools/desktop-ai-power) | 第一版必须清楚区分可编辑方案、预览和成片；用户可回到局部继续改。 |
| 用户希望“只改我说的，其他保持不动”，并希望先看到修改的参考再投入生成。 | Runway 的公开编辑流为上传素材、描述修改、先预览参考帧、再生成；其产品文案明确强调局部修改与保留其余内容。[Runway AI Video Editor](https://runway.com/product/ai-video-editor) | 局部修改不能只在后台有 scope；前端需让用户确认目标、保留项、预计影响和实际差异。 |
| 用户会用参考图/样片、首尾帧、延展、插入/移除和声音完成多轮细化。 | Flow 公开提供多参考图、首尾帧、延展、局部插入/移除及音频控制。[Google Flow / Veo 更新](https://blog.google/innovation-and-ai/products/veo-updates-flow/) | 样例/素材的用途必须明确；当前缺失的音频、局部视觉重绘等能力要诚实标注，不可把“计划”显示为“可完成”。 |

由此得到的产品重点不是“更多模型”或“更复杂聊天”，而是：

> **把用户的创作意图稳定地落为可编辑时间线，并让每次修改都能看见：改哪里、保留什么、实际改了什么、下一步还能做什么。**

这一定义来自用户行为预期；是否好用仍须由后文场景测试验证。

| **F-11 导出前的能力缺口** | 用户期待“导出成片”给出真实产物；若素材生成不可用，应在开始前说明。 | 单一 <code>timeline-delivery-readiness</code> 纯函数检查待处理修订、缺素材、Provider、外链和失败 job；UI/Agent 预判与正式 <code>executeV2TimelineDraftRun</code> 都调用它。 | **[已修复]** 直接 HTTP 也无法绕过；门禁在幂等 Receipt 和 RenderRun 创建前执行，确认版本过期返回冲突。 | 后续只完善提示可用性，不复制第二份门禁。 | 30 个故意缺条件的方案：所有入口阻断原因一致；阻断请求创建 RenderRun 数为 0。 |
| **F-12 样例理解与创作记忆** | 用户希望“沿用我认可的风格”，但不希望系统悄悄套用错误偏好。 | 创作偏好页显示来源及“已启用 / 待观察 / 已停用”；Planner 另在 <code>creative_brief.applied_preferences</code> 中声明实际采用项，服务端只接受本轮召回或原方案已采用的原文，方案 UI 单独展示。 | **[已修复工程事实边界]** “被召回”和“被采用”已分开；是否采用得当仍属于规划质量，需要评测而不能由字段存在证明。 | 保持采用项来自同一 creative brief，不复制一套前端推断逻辑。 | 带相似/冲突历史偏好的任务：未召回偏好写入采用项数量为 0；不该应用的偏好误用率为 0；用户能指出本次用了哪些偏好的比例 ≥90%。 |

~~~mermaid

  U["用户自然语言：第二镜更有冲击力，但别动卖点"] --> M["模型解析：选择 target、scope、instruction"]
  M --> V["结构校验：Zod、存在性、授权与范围过滤"]
  V --> P["生成候选时间线"]
  P --> R["结果审查：实际 diff、空改/范围漂移"]
  R --> O["用户看见并确认：目标、保留项、实际变化"]
~~~

| 层次 | 当前覆盖 | 仍不能证明什么 |
| --- | --- | --- |
| 结构合法 | <code>registry.ts</code> 限定 scope 枚举和参数形状；<code>dispatcher.ts</code> 检查 ID 是否属于当前草稿。 | “第二镜”是否被模型解析成正确 sceneId；“冲击力”究竟应改字幕、节奏、镜头还是素材。 |
| 范围约束 | <code>timeline-revision-scope.ts</code> 与 <code>evaluateV2TimelineRevisionCommit</code> 防止部分范围外字段落库；现有 smoke 覆盖字幕 scope 等。 | 用户真正想保留的东西是否已被表达为 scope 之外的字段；例如“不要动卖点”不是当前结构化 preserve 条款。 |
| 结果真实性 | <code>timeline-revision-outcome-review.ts</code> 计算字段 diff，能拒绝没有任何实际变化、部分无关变化等情况。 | 结果虽有变化，是否符合用户的主观意图；也不能替用户确认创作质量。 |

因此优化重点不是继续叠加隐藏检查，而是把模型的中间解释暴露为用户可校正的**修改确认卡**，再用最终 diff 证明执行结果。

## 6. 建议的核心产品界面与协议

### 6.1 修改确认卡（最高优先级）

任何已有方案上的自然语言修改，统一产生下列对象：

| 字段 | 来源 | 用户行为 |
| --- | --- | --- |
| 原始要求 | 用户原话，不可被模型改写覆盖 | 可查看上下文。 |
| 目标 | 对象身份由服务端绑定；卡片只显示人类可读名称和时间范围 | 可改选；不唯一时系统不执行。 |
| 修改范围 | subtitle / scene / structure / visual_strategy / transition / global | 可收窄或确认。 |
| 必须保留 | 用户明确说出的保留项，或从已确认规则带入 | 可添加、删除、确认。 |
| 预计影响 | 将变化的镜头、字幕、素材任务、时长 | 执行前预览。 |
| 实际变化 | 从 <code>describeV2TimelineSpecDiff</code> 生成的结构化 diff | 执行后核对。 |
| 状态 | 待澄清、待执行、已执行、失败、待用户确认、已拒绝 | 不能用“成功”掩盖失败或仅备注。 |
| 不满意原因 | 目标错、范围错、保留项受损、生成质量、事实/文案、偏好变化、素材缺失 | 形成下一轮正确输入。 |

P0 已落地统一 Intent、持久化待确认提案、从权威 spec 派生的可读目标与时间范围、终态 Receipt、actual diff 与确认/拒绝/纠正入口。固定不满意原因已经能带回澄清对话；仍未落地的是卡片内直接改选目标/范围/保留项、跨设备反馈统计和自动连续失败判断，这些属于 P1，而不是继续扩充 P0 修订协议。

### 6.2 方案状态卡

每个镜头只显示一种明确状态，避免用户把预览占位误认成成片：

| 状态 | 判断源 | UI 必须显示 |
| --- | --- | --- |
| 用户素材 | <code>scene.type === user_video</code> | 素材名称、是否裁切/适配。 |
| 已解析 AI 视频 | material job 已 fulfilled 且 output asset 为 <code>generated_asset</code> | 已生成/可渲染，真实资产名称。 |
| 待生成，预览兜底 | generation job 是 planned | “当前为预览卡，不是最终画面”、将调用的能力。 |
| 库存/本地/兜底/程序化 | output asset 或 scene asset 的权威 source，或 <code>remotion_card</code> | 具体来源类型与资产名称，不得显示为 AI 已生成。 |
| 失败或缺素材 | readiness / material job 状态 | 失败原因、需要用户补什么、不能导出的原因。 |

### 6.3 失败恢复卡

不要仅输出技术日志。统一把失败映射为用户选择：

| 失败类型 | 用户看到的下一步 |
| --- | --- |
| 目标不存在或不唯一 | 重新选择目标镜头/字幕。 |
| 需求不完整或冲突 | 补充“保留什么 / 以什么为准”。 |
| 修改没有产生实际 diff | 更具体地描述要改变的视觉或文字。 |
| scope 外变化 | 查看被阻止的内容，收窄范围或明确允许全局修改。 |
| 素材/provider 不可用 | 补素材、切换为现有素材方案或明确配置能力。 |
| 生成/渲染失败 | 保留草稿和失败状态，重试或修改方案；绝不回退后宣称已完成。 |

### 应对外凸显的产品重点

只有完成 P0 且通过后文指标后，以下三项才可以作为产品重点：

1. **可编辑方案，不是一次性黑盒成片**：用户能从镜头、素材、字幕和转场进入修改。
2. **受控局部修改**：先确认“改哪里、保留什么”，再执行；不确定就澄清。
3. **真实结果回执**：用户看到的是实际 diff、失败和待办，而不是模型的一句“已完成”。

时间线、scope、trace、幂等和审查器是实现这三项的基础，不是需要直接展示给用户的卖点。

## 8. 评测与高频测试

### 8.1 把“反复改不对”归因

| 分类 | 判定方法 | 对应优化 |
| --- | --- | --- |
| 意图缺失/冲突 | 原话没有唯一目标，或缺少保留项；系统仍直接执行。 | F-01、F-05 的确认与澄清。 |
| 解析错误 | 人工 gold 中目标明确，模型却选错 target/scope。 | 路由、提示词、确认卡纠正。 |
| 执行错误 | 合同正确，但持久化 revision/实际 diff 不符合合同。 | patch、版本、范围审查和回归。 |
| 能力不可用 | provider、素材、音频或渲染不支持/失败。 | F-04、F-11 的状态与预飞检查。 |
| 偏好变化 | 先前合同已满足，用户看结果后提出新方向。 | 记录为新 revision，不算模型理解失败。 |

### 8.2 现有评测与缺口

**[已验证代码]** <code>backend/evaluation/README.md</code> 已有确定性、live、stability、canary 四类入口；可评测草稿、修订、样例理解、幂等和部分真实 render。默认禁止视频生成 provider，样例视频当前只有 2 条，因此不能把现有总分当作真实创作成功率。

必须补充的真实场景集：

| 场景集 | 最少覆盖 | 主指标 |
| --- | --- | --- |
| 首次创建 | 有/无素材、有/无样例、文字限制冲突 | 创作摘要正确率、素材用途正确率、方案状态识别率。 |
| 局部修改 | 字幕、单镜头、视觉策略、结构、转场、全局；每类含“保留项”。 | 目标+scope 准确率、scope 外变化率、空改率。 |
| 不明确修改 | “这里”“更高级”“保留卖点”等指代/偏好语句。 | 澄清率、歧义误执行率。 |
| 失败恢复 | 缺素材、provider 不可用、生成失败、断网、取消、版本冲突。 | 用户可理解下一步比例、恢复成功率、假完成率。 |
| 高频交互 | 慢网上传立即发送、连点、双窗口、刷新后重放。 | 附件遗漏率、重复执行率、旧版本覆盖率、未发送输入保留率。 |

### 8.3 核心指标

| 指标 | 计算 | 建议门槛 |
| --- | --- | --- |
| 附件遗漏率 | 用户意图带素材但实际请求无对应素材 / 此类请求 | 0% |
| 方案状态误解率 | 把待生成/兜底/失败状态判断错的用户 / 参与者 | 0% |
| 唯一目标解析准确率 | target 和 scope 均与人工 gold 一致 / 目标唯一样本 | ≥95% |
| 歧义误执行率 | 标注为歧义却直接执行 / 歧义样本 | 0% |
| scope 外变化率 | 未授权字段变化 / 有 scope 的修订 | 0% |
| 假完成率 | 未产生有效 revision/diff 却显示已修改或完成 / 完成提示 | 0% |
| 失败可行动率 | 测试者无需技术人员即可说出并完成下一步 / 失败任务 | ≥90% |
| 恢复后重复执行率 | 同一意图产生重复工具/渲染执行 / 重试任务 | 0% |
| 修订可归因率 | 可归入五类失败之一的未满意修订 / 全部未满意修订 | ≥90% |

## 9. 完成顺序与验收

1. **先做可见性，不先堆能力。** 修复 F-06、F-02，增加方案状态、修改确认和实际 diff。
2. **再做可恢复性。** 把 F-08 至 F-10 的失败、取消、冲突转为用户可理解的状态与操作。
3. **最后再扩能力。** 当 P0 指标达标后，再决定是否补音频、更多生成方式或更复杂编辑。

功能完成不以“代码能运行”判定，而以以下三件事同时成立判定：

- 用户在执行前能说清系统将修改什么、保留什么；
- 执行后用户能直接看到实际变化，未执行时不会被告知“已完成”；
- 高频中断、慢网、重复操作和失败后，用户不丢失意图且知道下一步。

满足这三项后，当前项目的重点才会从“内部有很多校验”变成用户真正感受到的：**可控、可编辑、可解释的 AI 视频创作过程。**
